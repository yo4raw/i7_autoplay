## 17.4 実機ナビゲーション情報（検証済み・最重要）

> **【最重要】ループ対象画面への入口**
> ホーム画面 **右側** に「EVENT」バナーと「NanaPass」バナーが並んでおり、
> **「EVENT」バナーを押した遷移先のイベント画面が、本ツールの周回（ループ）対象** である。
> （ユーザー指定。NanaPass は対象外なので押さないこと。）

### 検証済み環境・座標（2026-06-04 時点）
- 実機ゲーム: アイドリッシュセブン（ホーム画面は **横画面**）
- iPhone ミラーリングウィンドウ: owner=`iPhoneミラーリング`, サイズ 529×334pt, スケール 2.0
  （キャプチャ解像度 1058×668px）。**ウィンドウサイズは固定前提。**
- 座標はすべて **ウィンドウ相対の小数（0.0〜1.0）** で記録（サイズ変化に頑健）。

### ホーム画面の要素位置（小数座標）
| 要素 | 位置 (xf, yf) | 備考 |
|------|--------------|------|
| 下部ナビ: HOME / LIVE / STORY / MEMBER / AUDITION / SHOWCASE / HALL / WORK / MENU | y≈0.93 の横帯 | MENU は (0.95, 0.93) で開く |
| スタミナ表示 | 左上 (♥ 現在/最大) | OCR 対象 ROI |

### 検証済み遷移
1. **ホーム → イベントページ**: EVENT バナー (0.79, 0.60) をタップ
   → イベントページ「**BUDDY Night NARRATIVE**」に遷移（順位表示・イベント情報・右下にボタン群）。
   ※ 実装の `home_marker` / `event_page_marker` テンプレはこの2画面から取得する。
2. **イベントページ初回表示時のポップアップ「本日の課題」**:
   - イベントページに入ると「**本日の課題**」ポップアップ（デイリー課題一覧）が表示される。
   - **1日1回のみ表示**される。**右上の ❌（× ボタン, 約 (0.80, 0.13)）で閉じる**こと。
   - ポップアップ内の「イベント楽曲へ」ボタンは**使わない**（正規フローは × で閉じる）。
   - このイベントは「累計 イベントライブを7回クリア」「累計 イベントライブでコンボ1500達成」
     「累計 イベントライブでスコア3700000達成」等の**累計課題**を持つ＝累計イベントであることを確認。
   - 実装上、`popup_daily_mission` テンプレ（「本日の課題」見出し）を検出したら × で閉じる。
3. **「獲得一覧」ポップアップ**:
   - 課題達成報酬の通知（例: 「イベント課題1つ目の達成報酬です。ステラストーン×1」）。
   - これも **右上の ❌ で閉じる**（ユーザー指定）。報酬はメールボックスから後で受け取れる。
   - 実装上、`popup_reward_list` テンプレ（「獲得一覧」見出し）を検出したら × で閉じる。
4. **クリーンなイベントページ（ループ対象画面）の下部ボタン**:
   - 下部右に **交換所 / 報酬一覧 / イベント楽曲** が並ぶ。
   - **「イベント楽曲」ボタン（下部右、約 (0.78, 0.93)）がライブ選択への入口**。
   - 画面下部に「次の体力回復時間」「設定」表示あり。

> **ポップアップ処理の原則（実機で確認）**: イベント遷移直後に複数のポップアップが
> 連続表示され得る（本日の課題 → 獲得一覧 …）。いずれも **右上の ❌（× ボタン）で閉じる**。
> ポップアップが無くなる（イベントページのマーカーが見える）まで × クローズを繰り返す。
> × の位置はポップアップ枠の右上角にあり、枠サイズで上下するため、テンプレ
> `popup_close_x` で検出してクリックするのが堅牢（座標直打ちは枠ごとにズレる）。

5. **イベントメインページ → イベント楽曲（楽曲選択）**: 「イベント楽曲」(0.78, 0.92) をタップ。
   - 初回は **データダウンロード確認ダイアログ**（例: 「約5.37MBのデータをダウンロードします」）が
     出る場合がある。**ダウンロード確認が出たら必ず「ダウンロード」ボタン（約 (0.63, 0.79)）を押す**
     （ユーザー指定）。`dialog_download` テンプレ検出 → 「ダウンロード」押下。
   - → **楽曲選択画面**に遷移。
6. **楽曲選択画面の要素**:
   - 左: 楽曲リスト（SOL/TRIGGER, NO DOUBT, Four Seasons Blue 等）。
   - 右上: **難易度選択**（EASY/NORMAL/HARD/… を ◀▶ で切替）。
   - 下部: **「ブースト OFF」「オート OFF」トグル**（← AUTO 設定はここ。要 ON 化）。
   - 右下: **「NEXT」ボタン**（緑、楽曲決定で次へ）。
   - 実装テンプレ: `song_select_marker`（NEXT ボタンや難易度セレクタ）、`auto_toggle_off`/`auto_toggle_on`、
     `boost_toggle_off`/`boost_toggle_on`、`next_button`。
   - **【難易度: 必ず EASY+ にすること（ユーザー指定）】**
     - 楽曲は **どれでもよい**が、難易度は **必ず EASY+ 固定**。
     - 難易度は画面中央右の **緑バナー「EASY+」**（★評価・BEST SCORE・楽曲タイプ円グラフの上）に表示。
       バナー位置 ≈ (0.83, 0.30)。現状すでに EASY+。
     - 実装上は `difficulty_easyplus` テンプレ（緑「EASY+」バナー）が表示されていることを確認し、
       異なる場合のみ切替操作を行う。切替UIの正確な操作は要追加調査（バナー/サイドのタップで切替）。
7. **【最重要発見】ゲーム内蔵の一括設定ダイアログ（ブースト/オート/ループ/自動回復）**:
   楽曲選択画面 下部の **「ブースト ◯◯／オート ◯◯」パネル（約 (0.55, 0.89)）をタップ**すると、
   ゲーム内蔵の設定ダイアログが開く。内容（実機確認）:
   - **ライブブースト**: `OFF / 2倍 / 3倍`（消費ライフを増やし報酬倍化）。
     - 3倍ラジオ ≈ **(0.555, 0.26)**、2倍 ≈ (0.46, 0.26)、OFF ≈ (0.36, 0.26)。
   - **オートライブ**: `OFF / ON`（ON ≈ (0.45, 0.36)、OFF ≈ (0.36, 0.36)）。← **ゲーム内蔵 AUTO**。
   - **ループ**: `OFF / 2回 / 3回 / 4回 / 5回`（**ゲーム内蔵で最大5連戦**。
     オートライブ ON 等の条件で選択可能になる＝初期はグレーアウト）。
   - **ブリンクドリンク / ライブ回復** の所持数表示と **自動消費**:
     「※最大5ループまで指定のブリンクドリンク・ライブ回復を自動で行います。
     指定アイテムがなくなった場合、ループは自動で終了します」。
   - ダイアログ下部: **キャンセル ≈ (0.42, 0.87)／OK ≈ (0.625, 0.87)**。
   - 設定後、楽曲選択画面下部のパネルが赤くなり「ブースト 3倍／オート ○○」と表示される（設定済みの目印）。
   - ラジオ選択時に「○○について」ヘルプ説明オーバーレイが出ることがある → タップで閉じる（選択自体は成立済み）。

   > **【自動化戦略への影響・最重要】**
   > **ゲーム自体が「AUTO ＋ 最大5ループ ＋ スタミナ自動回復（ブリンクドリンク/ライブ回復）」を内蔵**している。
   > したがって本ツールの役割は大幅に簡素化できる:
   > 1. 設定ダイアログで **ブースト=3倍 / オート=ON / ループ=5回** を設定して OK
   > 2. ライブ開始 → ゲーム任せで5連戦（スタミナ自動回復含む）が走る
   > 3. **5ループ完了後**にツール側でリザルト/報酬を処理し、再度ライブ開始へ戻る、を繰り返す
   > 4. アイテム枯渇時はゲーム側がループ自動終了 → ツールが検知して停止
   >
   > 第6章 FSM の `STAMINA_RECOVER` や1回ごとのライブ周回は、**5連戦を1単位**とする
   > 粗いループに置き換えられ、ツールが送る操作回数・誤操作リスクが激減する。
   > （現状ユーザー指示で **ブースト=3倍** まで設定済み。オート/ループの既定値は今後確定。）

8. **NEXT 押下以降のフロー（2026-06-04 実機確認）**:
   - **NEXT (約 (0.86, 0.91))** → **フレンド（サポート）選択画面**へ。
     楽曲名の下に候補（フレンド）が一覧。**先頭の候補をタップ（約 (0.40, 0.42)）で選択**。
   - → **編成確認／ライブ開始画面**。右上に **「♥ -16」** と **「★ ×3」**（= このライブの
     **LIFE 消費 16・ブースト3倍**）。下部右に **START ボタン（約 (0.85, 0.91)）**。
   - **START** → 初回は曲データの **Downloading..**（数秒）→ ライブ開始（カウントダウン 3→2→1）。
   - ライブ進行 → リザルト → 報酬 のフロー詳細は本書「17.6 LIFE 回復・ゲーム内蔵オート設定の確定仕様（2026-06-04 実機調査・最重要）」参照。

## 17.6 LIFE 回復・ゲーム内蔵オート設定の確定仕様（2026-06-04 実機調査・最重要）

> **ユーザー要件**: 「**LIFE 回復は必ずきなこパンを使い、ステラ（ステラストーン）は使わない**」。
> 本節はその要件を満たすために実機で確認した仕様を記録する。

### (A) 楽曲選択下部の「ブースト／オート」パネル → ゲーム内蔵設定ダイアログ
楽曲選択画面 下部の「**ブースト ◯倍／オート ◯◯**」パネル（約 **(0.55, 0.89)**）をタップで開く。
ダイアログ内容と**実測座標（ウィンドウ相対小数, 529×334pt）**:

| 項目 | 選択肢と座標 (xf, yf) | 備考 |
|------|----------------------|------|
| ライブブースト | OFF / 2倍 / **3倍 (0.55, 0.26)** | 3倍 = LIFE 消費3倍・報酬倍化。**3倍 を使用（ユーザー指定）** |
| オートライブ | OFF (0.351, 0.357) / **ON (0.461, 0.357)** | ← (B) 参照。**グレードA未取得だと使用不可** |
| ループ | OFF/2回/3回/4回/**5回** (行 y≈0.452, OFF=0.351・2回=0.448・3回=0.543・4回=0.639・5回=0.735) | **オートライブ ON が前提**でないとグレーアウト |
| ブリンクドリンク | 所持数表示（自動消費枠） | 現所持 **0**。LIFE 回復用ドリンク |
| **ライフ回復（＝きなこパン）** | 所持数表示（自動消費枠） | アイコンは**黄金色のパン＝きなこパン**。現所持 **10** |
| キャンセル / OK | キャンセル (0.42, 0.87) / **OK (0.62, 0.87)** | |

注記文（原文）: 「※最大5ループまで**指定のブリンクドリンク・ライフ回復を自動で行います**。
**指定アイテムがなくなった場合、ループは自動で終了します**」。

> **【最重要・きなこパン/ステラ要件との関係】**
> ゲーム内蔵ループの自動回復は **ブリンクドリンク と ライフ回復（きなこパン）のみ**を消費し、
> **アイテムが尽きるとループを自動終了する＝ステラは絶対に消費しない**。
> よって「きなこパンで回復・ステラ不使用」の要件に**本質的に合致**する安全な仕組みである。
> ただし下記 (B) の制約により、現状この内蔵ループは使えない。

### (B) オートライブはグレードA以上が必要（内蔵ループが使えない理由）
オートライブ ON を選ぶと「**オートライブを使用するにはグレードをA以上取る必要があります**」
というポップアップが出て、ボタンが「**グレードが足りません**」となり ON にできない。
→ **ゲーム内蔵の AUTO＋5ループ＋自動回復は、当該難易度でグレードA以上を一度取るまで使えない**。
→ 現状は [architecture.md](architecture.md) §17.5 の「**ツール側で円を連打して手動クリア → もう一度 → 次のライブ**」方式（Path B）を継続する。

> **【2026-07-31 解禁 → ただし不使用】** ツール周回の積み重ねでグレードA条件を満たし、
> **オートライブ ON が選択可能になった**（実測は [device-findings.md](device-findings.md)
> 「ゲーム内蔵オートライブの実機検証」参照）。上記の制約記述は歴史的経緯として残す。
> オートライブは**1ライブにつきブリンドリンク3個を消費**する（所持数プレビューで確認。
> このときの在庫: ブリンドリンク201・ライフ回復182）。
> **→ ユーザー方針: ドリンクを消費するためオートは使わない。周回はオート OFF・
> tap エンジンで行い、EASY で SS グレードを目指す。**
>
> **⚠️ 2026-07-31 の検証でゲーム側設定が「オート ON」のまま残っている。次回の周回開始時、
> このダイアログで OFF に戻し、パネルが「ブースト 3倍／オート OFF」表示になってから
> START すること**（ON のままだとドリンクが消費され続ける）。
>
> **671×348 ウィンドウでの実測座標**（上表は 529×334pt での値。機種/ウィンドウで異なる）:
> 設定パネル (0.577, 0.828) / オートライブ OFF (0.360, 0.353)・ON (0.466, 0.353) /
> OK (0.594, 0.845)。

### (D-LIFE) LIFE 回復ダイアログ＝きなこパンで回復（ステラ厳禁）— 2026-06-04 実測・実装済み
「はい（再プレイ）」時に LIFE が消費16に満たないと **LIFE 不足ダイアログ**が出る。実測した構成:

```
┌───────────────────────────────────────────────┐
│  [ ライフが足りません。 ]      LIFE ♥ 10        │
│  ┌─────────────────────────────────────────┐  │
│  │ 🥯  きなこパン : LIFE 20 回復             │  │   ← 上段。これを使う
│  │ 所持 10   [ - 1 + ]        [ 回復 ]◀━━━━━┿━━ (0.644, 0.508) 窓相対
│  └─────────────────────────────────────────┘  │
│  ┌─────────────────────────────────────────┐  │
│  │ ✦  ステラストーン : LIFE 全回復           │  │   ← 下段。**絶対に押さない**
│  │ 所持 163  [ 3 ]            [ 回復 ]       │  │      (約 (0.644, 0.69) 窓相対)
│  └─────────────────────────────────────────┘  │   × ボタン: 右端 (0.814, 0.50)
└───────────────────────────────────────────────┘
```

**確定フロー（実装済み・実機で確認）**:
1. `life_short.png`（「ライフが足りません。」見出し, score≈1.0）を検出 → **state=lifeshort**。
   ※判定は friendreq より前に置き、未知メニュー扱いで盲目タップ→ステラ誤押下を防ぐ。
2. **きなこパンの「回復」(窓相対 (0.644, 0.508)) をクリック**（数量1。きなこパン1個=LIFE+20）。
3. → 「**ライフを20回復しました。 LIFE 12 ▶ LIFE 32**」確認ポップアップ
   → **× (窓相対 (0.78, 0.41)) で閉じる**。
4. → そのまま次のライブが開始（Downloading→ゲームプレイ）。きなこパン所持が 1 減る。

**ステラ不使用の保証（多重）**:
- ステラの「回復」ボタン(下段)の座標は**コードに一切持たせず、クリックしない**。
- LIFE 不足が `MAX_LIFE_RECOVERS`(=6) 回連続したら（=きなこパン枯渇）、
  `life_depleted_*.png` を保存して**停止**（ステラには絶対にフォールバックしない）。
- 未知ダイアログは従来どおり `STUCK_STOP_SEC`(=25秒) で停止（盲目クリック廃止済み）。

**座標系の注意（実装で対応済み）**: スクショは全ウィンドウ＝**ウィンドウ相対**。一方
`click_content` は内容矩形(38..325)相対で Y がズ레る。LIFE 回復・再プレイ「はい」・Result
送りなど**スクショ実測座標は `click_window`（ウィンドウ相対）でクリック**する。
きなこパン行とステラ行は近接するため、この区別は誤押下防止に必須。

### (D) PAUSE メニューの正確な仕様（重大バグ修正済み）
ライブ中にミラーリングのフォーカスが外れると **PAUSE メニュー**が出る。構成（実測）:
- 見出し「**PAUSE**」（上中央）、右上に「スキル」ボタン。
- 楽曲名（SOL / TRIGGER 等）、Music音量／タップ音量／スキル発動音量スライダー。

### (E) ゲームプレイ中の自動 PAUSE は intrinsic（最重要・実験で確定）
ライブ中、ゲームが**自分の PAUSE メニューを定期的に表示**する。複数の制御実験で原因を切り分けた:

| 実験 | 操作内容 | 結果（PAUSE までの時間 / 頻度） |
|------|----------|--------------------------------|
| 純粋オブザーバ | grab のみ・クリック/activate/カーソル一切なし | ゲーム開始 **0.7秒**で PAUSE、以後 30秒そのまま |
| カーソルジグル | 実カーソルを 1.2s ごとに移動(warp+moved) | 40秒で **9回**（≈4.7秒周期、baseline と同じ＝無効） |
| 高頻度連打 | 円を 0.03s ごと(≈32回/秒)に連続タップ | 再開後 **約3〜5秒**で PAUSE |
| カーソル同位置クリック | warp+moved+click を各タップ点で実施 | 30秒で **7回**（baseline 同等＝無効） |
| caffeinate | `caffeinate -disu`（アイドル/スリープ/表示抑止+活動宣言） | 効果なし |
| autolive(run3) | 円連打＋0.4s ごと activate_fast | 600秒で **129回**（≈4.7秒周期）、0クリア |

**確定した事実**:
- iPhone ミラーリングは PAUSE 中も**フロントモスト＆アクティブ**（`isActive()==True`）。
  → **フォーカス喪失が原因ではない**。ホスト側コマンド実行（ポーリング）も無関係だった。
- **合成クリック(CGEvent)も実カーソル移動も、PAUSE を完全には防げない**。
  ただし**タップは PAUSE 到来を遅延**させる（無操作 0.7秒 → 連打時 6〜8秒）。
- これは **iPhone ミラーリング経由で iOS アプリが定期的に inactive 化（background 相当）し、
  ゲームが resignActive で PAUSE メニューを出す**挙動と考えられる。genuine な実機タッチが
  ないと iOS 側がアプリをアイドル扱いする、プラットフォーム由来の制約。

**結論（複数実験で確定）**:
- **Mac 側のいかなる合成入力（クリック・カーソル移動・カーソル同位置クリック・caffeinate）でも
  この PAUSE は防げない**。アプリはフロントモスト・アクティブのまま、ゲームが定期的に PAUSE する。
- **mss の画面取得(grab)も無関係**（grab を一切せず18秒タップし続けても PAUSE する＝grab は原因でも
  防止策でもない）。
- PAUSE 周期が短い（≈3〜5秒）場合は再開カウントダウンの巻き戻しで**新規曲がほぼ進まない**。
  **決定的検証: 無人で 42分・691回の PAUSE→再開 を繰り返しても 0 クリア**（1曲も完走せず）。
  691サイクルあれば net 進行が少しでも正なら必ず完走するはずで、完走しない＝
  **mss ミラーリングの app-suspension からの「再開」は曲を巻き戻し、再生分を相殺する**
  （実質「待てば終わる」問題ではない）と確定。
- 過去に観測した完走（Result 到達）は、**PAUSE が起きない連続再生ウィンドウ**（=実機操作・
  在席条件）で得られたものであり、無人の再開サイクル累積では得られない。
- **帰結: 無人・完全自動での連続クリアは、この PAUSE が起きる環境では不可能**。
  正常動作には PAUSE が起きない条件（iPhone 自動ロック無効＋実行中の在席で genuine 入力を
  供給）が必須。これはプラットフォーム制約であり、本ツールのコードでは解決できない。
- **PAUSE があっても曲は net で進行し、累積タップで必ず完走する**（実機で複数回 Result 到達を確認）。
  ただし効率が低く（再開ごとに 3秒カウントダウン＋わずかな巻き戻し）、**PAUSE 多発条件下では
  1ライブの実完走に 8〜10分程度**かかる（300〜480秒では未完のことがある）。

**帰結（実装方針）**:
- PAUSE は不可避と割り切り、**検出したら即・再開**（`P_RESUME=(0.69,0.76)`）。再開直後の
  カウントダウンは暗い＝gameplay 扱いなのでそのままタップ円連打を継続 → 自然に曲が進む。
- **本ツールは「PAUSE を高速に再開し続ける」ことで、低速ながらライブを連続クリアし続ける**。
- 運用上の最善策（ユーザー向け・高速化）: **iPhone の自動ロックを「なし」にし、実行中は
  Mac に物理的に在席して時々トラックパッド等を操作する**。genuine な実機/HID 入力がある条件では
  PAUSE がほぼ起きず 1ライブ≈90秒で回る（[architecture.md](architecture.md) §17.5 の初期検証はこの条件下だったと推定）。

> **【重要・後日解決】上記「ソフト側からの根本回避は確認できていない」は [device-findings.md](device-findings.md)「PAUSE の解決策（2026-06-05）」で解決した。**
> 通常の合成クリック（`source=None`）が genuine 入力として扱われなかったのが原因で、
> **HIDSystemState のイベントソース**で実カーソルを動かしてクリックすれば PAUSE は起きない。

## 5.2 スタミナ回復機能
- スタミナ不足ダイアログを検知（テンプレ）。
- `stamina.recover_enabled=true` の場合、指定アイテム（`stamina.item`）を選択・使用・確定。
- 1周回あたりの回復試行回数を `stamina.max_recover_per_loop` で上限管理。
- 在庫切れ表示を検知したら、`stop_on_item_depletion` に従い停止判定へ。

### LIFE 表示はブースト込みの実消費値

**難易度タブに出る LIFE 15 / 30 / 45 / 60 は、ブースト3倍を適用した後の実消費値**（素の消費は 5 / 10 / 15 / 20）。
フレンド選択画面のヘッダも `♥ -15` と 3 倍適用後の値を出す。
「ブーストが効いていないのでは」と誤読しやすいので注意する。
既出の「LIFE 消費 = 16（ブースト3倍時）」も同じ性質の値。

ブーストが設定済みかどうかは、楽曲選択・編成画面の下部パネルが
`ブースト 3倍 / オート OFF` と表示されているかで判断する。

### フレンド選択のタップは1回目が無視されることがある

画面遷移アニメーション中のタップは効かない。フレンド行が3件描画されきってから
もう一度タップすると通る。`autolive.py` は再試行するので実害は無いが、
手動ナビゲーション時は 0.8〜1.5 秒待ってから撮り直すこと。
