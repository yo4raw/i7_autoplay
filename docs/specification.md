## 1. 概要

### 1.1 目的
アイドリッシュセブン（以下 IDOLiSH7）の「累計イベント」における、ライブ（リズムゲーム）の
AUTO 周回作業を、macOS の **iPhone ミラーリング** 経由で自動化する Python プログラムの
仕様を定義する。単調な周回操作を無人で繰り返し、累計ポイントを蓄積することを目的とする。

### 1.2 背景
累計イベントは、規定のライブを AUTO で何度も繰り返してポイントを稼ぐ作業ゲー要素が強い。
手動周回は拘束時間が長く負担が大きいため、画面認識ベースの自動化により省力化する。

### 1.3 用語定義
| 用語 | 定義 |
|------|------|
| 周回 | ライブを1回プレイして報酬を受け取る一連の流れ |
| 累計pt | イベントで蓄積される累計ポイント |
| AUTO | ゲーム内の自動演奏モード |
| iPhone ミラーリング | macOS Sequoia 以降の、iPhone 画面を Mac に表示・操作する機能 |
| テンプレートマッチング | 参照画像を画面内から探索して一致箇所を特定する画像認識手法 |
| FSM | 有限状態機械（Finite State Machine）。本ツールの制御モデル |
| TCC | macOS のプライバシー権限管理（Transparency, Consent, and Control） |
| ROI | 関心領域（Region of Interest）。認識・OCR を限定する画面範囲 |

### 1.4 対象読者・位置づけ
本書は本ツールの開発者・利用者を対象とする。実装フェーズの設計土台であり、ゲーム UI の
更新に応じて改訂される前提のドラフトである。

## 2. 前提条件・動作環境

### 2.1 ハードウェア
- Mac 本体（Apple Silicon / Intel いずれも可）
- iPhone 実機（IDOLiSH7 インストール済み、Mac と同一 Apple ID・近接・Bluetooth/Wi‑Fi 有効）

### 2.2 ソフトウェア
- **macOS Sequoia 15.0 以上**（iPhone ミラーリング機能が利用可能なこと）
- **iPhone ミラーリング** アプリ（接続確立済み・実行中・前面表示可能なこと）
- **Python 3.11 以上**

### 2.3 主要依存ライブラリ（詳細は第14章）
`opencv-python` / `numpy` / `Pillow` / `mss` / `pyobjc-framework-Quartz` /
`pyobjc-framework-AppKit` / `ocrmac`（Apple Vision OCR）/ `PyYAML` / `pydantic` /
`typer` / `pynput`

### 2.4 事前セットアップ（権限付与・接続）
本ツールは macOS の TCC 権限を **2つ** 必要とする。付与対象は **本ツールを起動するホスト
プロセス**（Terminal / iTerm / VS Code など）であり、スクリプトファイルではない点に注意。

1. **画面録画（Screen Recording）**: `システム設定 → プライバシーとセキュリティ → 画面収録`
   で実行ホストを許可。→ 画面キャプチャに必要。
2. **アクセシビリティ（Accessibility）**: `システム設定 → プライバシーとセキュリティ →
   アクセシビリティ` で実行ホストを許可。→ 他アプリへの合成クリック（CGEvent）に必要。

> 権限付与後は **実行ホストを再起動**（ターミナル等を開き直す）こと。
> macOS のアップデート後に権限が無効化され、**無言で失敗**することがある（第16章）。

3. iPhone ミラーリングを起動して接続を確立し、IDOLiSH7 を起動した状態にしておく。

### 2.5 ディスプレイ・ウィンドウ固定（v1 の前提）
テンプレートマッチングは UI の表示サイズに依存するため、**テンプレ画像を取得したときと
同じウィンドウサイズ・ディスプレイ解像度・スケーリング** で運用すること。
v1 ではミラーリングウィンドウのサイズ固定を前提とし、起動時にサイズ不一致を検出した場合は
警告する（マルチスケール対応は将来拡張）。

## 3. スコープ

### 3.1 対象範囲
- ① ライブ/バトルの周回（開始 → AUTO 進行 → クリア → 報酬受け取り → 繰り返し）
- ② スタミナ回復（不足検知 → ドリンク/回復アイテム使用 → 在庫管理）
- ③ ポップアップ処理（レベルアップ・ログインボーナス・お知らせ・通信エラー等の自動クローズ）
- ④ 停止条件判定（目標周回数到達・アイテム枯渇・連続エラー・手動キルスイッチ）
- ⑤ 進捗トラッキング（周回数カウント、累計pt/スタミナ残量の OCR 取得・記録）

### 3.2 非対象範囲
- ガチャ・課金操作（一切行わない）
- ストーリー進行・初回設定・チュートリアル
- 編成（ユニット）の自動最適化（現状の編成のまま「決定」のみ）
- 複数アカウントの切替・同時運用

### 3.3 制約事項
- ゲーム UI の更新時はテンプレ画像の差し替え／再取得が必要（破綻し得る）。
- 実行中は iPhone ミラーリングが最前面を占有する（第4章・第16章）。

## 4. システム構成・アーキテクチャ

### 4.1 全体構成（メインループ）
```
        ┌─────────────────────────────────────────────┐
        │                 State Machine                │
        │  (周回 / ポップアップ / スタミナ / 停止条件)  │
        └───────▲──────────────────────────┬──────────┘
                │ 認識結果                  │ 操作指示
        ┌───────┴───────┐          ┌───────▼───────┐
        │  Recognition  │          │   Actuator    │
        │ Template/OCR  │          │ 最前面化+Click │
        └───────▲───────┘          └───────┬───────┘
                │ 画像                      │ CGEvent
        ┌───────┴───────┐          ┌───────▼───────────┐
        │   Capture     │          │ iPhone Mirroring   │
        │ (mss→crop)    │◄─────────┤  Window (前面)     │
        └───────────────┘  screen  └────────────────────┘
```
処理は「**キャプチャ → 認識 → 状態判定 → 操作**」を1サイクルとするループ。

### 4.2 コンポーネント分割
| 層 | 役割 |
|----|------|
| Capture（画面キャプチャ） | ミラーリングウィンドウ領域の画像取得（`mss` で全画面取得→クロップ） |
| Recognition（画像認識） | テンプレートマッチング・OCR で現画面状態と要素位置を特定 |
| State Machine（状態管理） | FSM。現状態の判定・アクション選択・遷移制御 |
| Actuator（操作実行） | ミラーリング最前面化 → CGEvent によるタップ/スワイプ |
| Config / Logger / Safety | 設定読込・ログ出力・キルスイッチ・ウォッチドッグ |

### 4.3 最重要の技術制約（設計を規定）

> **iPhone ミラーリングへの合成クリック（CGEvent）は、macOS が入力を「最前面アプリ」に
> のみルーティングするため、iPhone ミラーリングが最前面かつ同一 Space にある間しか
> 機能しない。** バックグラウンドウィンドウへ直接入力を注入する API は存在しない。

帰結:
- **実行中は iPhone ミラーリングが画面を占有**する（Mac を他作業に使えない）。専用周回前提。
- 各操作の直前にミラーリングを `activate`（最前面化）し、短い settle 待ち（約 200ms）を入れる。
- 制御ターミナルとミラーリングウィンドウは **同一 Space**（同じデスクトップ）に置くこと。
- **ハードキルスイッチ = ミラーリングウィンドウを閉じる**（入力が即座に止まる）。
- `CGWindowListCreateImage` は macOS 15.0 で廃止 → キャプチャは `mss` を採用。
  ウィンドウの **列挙**（`CGWindowListCopyWindowInfo` による bounds 取得）は引き続き利用可。

### 4.4 座標系の扱い
- ミラーリングウィンドウ原点 `O=(Ox, Oy)` は **ポイント**（`kCGWindowBounds` より取得）。
- `mss` のキャプチャ画像は **ピクセル**（Retina では 2x）。
- スケール `s = NSScreen.backingScaleFactor`（**ハードコードせず実行時取得**。外部モニタでは 1.0 もあり得る）。
- 画像内マッチ位置 `(mx, my)`（ピクセル）→ クリック先の画面ポイント:
  `screen_pt = (Ox + mx/s, Oy + my/s)`。クリックはマッチ矩形の中心。
- 逆変換: `(px, py) = ((screen_x - Ox)*s, (screen_y - Oy)*s)`。

## 5. 機能要件

### 5.1 ライブ周回機能
FSM（第6章）に基づき、ホーム → イベントページ → ライブ選択 →（楽曲選択）→ 編成確認 →
スタミナ確認 → ライブ開始（AUTO 有効化）→ AUTO 進行待ち → リザルト → 報酬受け取り
→ ループ判定、を自動で繰り返す。「もう一度」ボタンがあればショートカット利用（設定可）。

### 5.2 スタミナ回復機能
- スタミナ不足ダイアログを検知（テンプレ）。
- `stamina.recover_enabled=true` の場合、指定アイテム（`stamina.item`）を選択・使用・確定。
- 1周回あたりの回復試行回数を `stamina.max_recover_per_loop` で上限管理。
- 在庫切れ表示を検知したら、`stop_on_item_depletion` に従い停止判定へ。

### 5.3 ポップアップ処理機能
- 各待機サイクルで、期待テンプレの前に **ポップアップ群を優先走査**。
- 対象: レベルアップ / ログインボーナス / お知らせ・告知 / 通信エラー / 汎用 OK・×・閉じる。
- 種別ごとの後処理（例: 通信エラーは「リトライ」優先）。閉じたら割込み元状態へ復帰。

### 5.4 停止条件機能
以下のいずれかで安全停止（または異常停止）:
1. 周回数 ≥ `target_loop_count`（→ SAFE_STOP）
2. 回復アイテム枯渇 かつ `stop_on_item_depletion=true`（→ SAFE_STOP・理由付き）
3. 累計pt ≥ `target_event_points`（OCR・任意機能、null で無効）（→ SAFE_STOP）
4. キルスイッチ押下（→ SAFE_STOP）
5. 連続エラー回数 ≥ `max_consecutive_errors`（→ ERROR_STOP）

### 5.5 進捗トラッキング
周回数（内部カウンタ）、累計pt・スタミナ残量（OCR・任意）を取得しログに記録。
停止時にサマリ（実行周回数・使用アイテム数・経過時間・停止理由）を出力。

## 7. テンプレート画像の管理

### 7.1 命名規則・ディレクトリ構成
```
assets/templates/
├── live/     # home_marker, event_page_marker, live_select_marker, song_select_marker,
│             # formation_marker, live_start_marker, playing_marker, result_marker,
│             # reward_marker, play_again_marker, auto_button_off, auto_button_on
├── stamina/  # stamina_confirm_marker, stamina_shortage_marker, recover_dialog_marker,
│             # drink_s, drink_m, item_empty_marker
└── popups/   # popup_levelup, popup_login_bonus, popup_notice, popup_network_error,
              # popup_generic_ok, popup_generic_close, back_button, home_button
```
- ファイル形式: PNG（アルファ不要、ロスレス）。
- 命名: スネークケース、状態/役割が分かる名前。設定の `stamina.item` 値はファイル名に対応。

### 7.2 必要テンプレ画像チェックリスト
付録17.1に集約。実機 UI をキャプチャして用意する。

### 7.3 マッチング方式・閾値
- `cv2.matchTemplate` + `TM_CCOEFF_NORMED`、相関スコア ≥ `match_threshold`（既定 0.85）でヒット。
- テンプレごとに閾値を上書きできる設計が望ましい（小アイコンは高め等）。
- 同一テンプレが複数ヒットする場合は最大スコア位置を採用。

### 7.4 解像度・スケーリング依存
- テンプレ取得時と同一ウィンドウサイズ・スケールでのみ正しく動作（v1）。
- 起動時に `mirroring.expected_resolution` と実ウィンドウサイズを照合し、不一致なら警告。
- ゲーム UI 更新・テーマ変更時は再取得が必要。

### 7.5 ROI（関心領域）
誤検出低減・高速化のため、状態ごとに探索範囲（ROI）を限定可能とする（例: ボタンは画面下部）。
OCR 対象（累計pt・スタミナ・周回数）も ROI を定義する（7章ではなく8章で詳述）。

## 8. OCR 仕様

### 8.1 読取り対象
- スタミナ残量（例: `120/120`）
- 累計pt（停止条件判定・任意）
- 周回/挑戦回数表示（あれば）

### 8.2 OCR エンジン・前処理
- エンジン: **Apple Vision（`ocrmac` 経由、言語 `jpn`）**。横書き数値に強く、追加バイナリ不要。
- 前処理: 対象 ROI をクロップ → 必要に応じ拡大・二値化・コントラスト調整。

### 8.3 認識結果の検証
- 正規表現で数字（および `/` 区切り）を抽出。
- 桁数・値域チェック（例: スタミナは 0〜上限、負値や桁あふれは無効として再取得 or テンプレ判定にフォールバック）。
- 可能な限り **テンプレ判定を優先** し、OCR は数値が必要な箇所に限定する。

## 9. 設定ファイル仕様

### 9.1 形式・配置
- 形式: **YAML**（既定）。配置: 既定 `config/default.yaml`、`--config` で上書き可能。
- 読込時に `pydantic` でスキーマ検証し、エラーは分かりやすく報告。

### 9.2 設定項目一覧
| キー | 型 | 既定 | 説明 |
|------|----|------|------|
| `target_loop_count` | int | 必須 | 目標周回数。到達で SAFE_STOP |
| `max_retries` | int | 3 | RECOVERY のリトライ上限。超過で ERROR_STOP |
| `max_consecutive_errors` | int | 5 | 連続エラー上限 |
| `template_dir` | str | `./assets/templates` | テンプレ画像ディレクトリ |
| `match_threshold` | float | 0.85 | テンプレマッチ相関閾値（0–1） |
| `action_delay` | float | 0.5 | クリック後の最小待機（秒） |
| `poll_interval` | float | 0.5 | 画面ポーリング間隔（秒） |
| `timeouts.default` | float | 15 | 状態別タイムアウト既定（秒） |
| `timeouts.live_playing` | float | 180 | AUTO 進行待ちタイムアウト（楽曲尺＋余裕） |
| `timeouts.<state>` | float | - | 各状態の個別上書き（任意） |
| `stamina.recover_enabled` | bool | true | スタミナ自動回復 ON/OFF |
| `stamina.item` | str | `drink_s` | 使用アイテム識別子（テンプレ名に対応） |
| `stamina.max_recover_per_loop` | int | 3 | 1周回あたり回復試行上限 |
| `stop_on_item_depletion` | bool | true | アイテム枯渇で停止するか |
| `target_event_points` | int\|null | null | 累計pt 目標（OCR、到達で停止／null で無効） |
| `live.difficulty` | str | `normal` | 選択する難易度 |
| `live.song` | str\|null | null | 選択楽曲（null で固定/先頭） |
| `use_play_again` | bool | true | 「もう一度」ショートカットを使うか |
| `log.level` | enum | `INFO` | DEBUG/INFO/WARNING/ERROR/CRITICAL |
| `log.file` | str | `./logs/autoplay.log` | ログファイルパス |
| `log.rotate_mb` | int | 10 | ローテーションサイズ（MB） |
| `log.save_debug_captures` | bool | false | 誤検出解析用スクショ保存 |
| `mirroring.window_title` | str | `iPhone Mirroring` | 対象ウィンドウ名（`iPhoneミラーリング` も内部で照合） |
| `mirroring.expected_resolution` | [int,int]\|null | null | 期待ウィンドウサイズ（ずれ検出用） |
| `kill_switch.hotkey` | str | `cmd+shift+q` | 緊急停止ホットキー |

### 9.3 設定例（`config/default.yaml`）
```yaml
target_loop_count: 50
max_retries: 3
max_consecutive_errors: 5

template_dir: ./assets/templates
match_threshold: 0.85
action_delay: 0.5
poll_interval: 0.5

timeouts:
  default: 15
  live_start: 30
  live_playing: 180
  result: 20

stamina:
  recover_enabled: true
  item: drink_s          # assets/templates/stamina/drink_s.png に対応
  max_recover_per_loop: 3

stop_on_item_depletion: true
target_event_points: null   # 例: 500000 で累計pt到達停止

live:
  difficulty: normal
  song: null

use_play_again: true

log:
  level: INFO
  file: ./logs/autoplay.log
  rotate_mb: 10
  save_debug_captures: false

mirroring:
  window_title: iPhone Mirroring
  expected_resolution: null   # 例: [402, 874]

kill_switch:
  hotkey: cmd+shift+q
```

## 10. ログ仕様
- 出力先: **stdout ＋ ファイル**（`log.file`、サイズローテーション `log.rotate_mb`）。
- レベル: DEBUG / INFO / WARNING / ERROR / CRITICAL（`log.level` で制御）。
- フォーマット: タイムスタンプ・レベル・**状態名**・アクション・認識スコア等を含む。
  例: `2026-06-04 12:00:00 INFO [S9 LIVE_PLAYING] result_marker matched score=0.93`
- デバッグキャプチャ: `log.save_debug_captures=true` で、ERROR 時や認識失敗時に画面スクショを保存。
- 停止時サマリ: 実行周回数・使用アイテム数・経過時間・停止理由を INFO で出力。

## 11. エラーハンドリング・リトライ方針
- **検知してから操作**（blind sleep を避ける）: 各ステップは「キャプチャ→期待アンカー一致→操作」。
  固定待機は焦点切替後の settle（約 200ms）程度に限定し、待機は **poll-until-condition**。
- **再認識リトライ**: マッチ失敗は再キャプチャで K 回リトライ → 既知の「閉じる/戻る」へフォールバック → 再アンカー。
- **不明画面の復帰（S14）**: `back_button`/`home_button` を順に試し、ホーム経由で再スタート。
- **焦点/Space 喪失**: 毎サイクルで最前面アプリを確認し、ミラーリングでなければ再 `activate`。
  ウィンドウが見つからない（アプリ終了・別 Space・iPhone 切断）場合は一時停止し明示メッセージ。
- **iPhone スリープ/黒画面**: 黒フレームへ連打しない。待機→復帰試行→不能なら SAFE_STOP。
- **連続エラー上限**: `max_consecutive_errors` 超過で ERROR_STOP（最終スクショ保存）。

## 12. CLI 仕様
- エントリポイント: `i7autoplay`（`typer` ベース）。
- サブコマンド:
  - `i7autoplay run` — 周回を実行。
  - `i7autoplay doctor` — 権限（画面録画・アクセシビリティ）とウィンドウ検出を診断。
  - `i7autoplay calibrate` — テンプレ取得補助・座標/スケール確認（既知点にマーカー描画）。
- 主なオプション:
  - `--config PATH`（設定ファイル）
  - `--dry-run`（実クリックせず FSM 遷移とクリック予定をログ出力）
  - `--target N`（`target_loop_count` 上書き）
  - `--log-level LEVEL`

## 13. セキュリティ・規約上の注意
- **ゲーム利用規約**: 多くのゲームは自動化・BOT・マクロ等を禁止しており、本ツールの利用は
  **規約違反となる可能性が高い**。違反時はアカウント停止・データ削除等の措置を受け得る。
- **自己責任**: 本ツールの利用は完全に自己責任で行うこと。開発者は一切の責任を負わない。
- **権限の取扱い**: 画面録画・アクセシビリティは強力な権限。信頼できる環境でのみ付与し、
  不要になったら無効化すること。本ツールは画面・入力を外部送信しない（ローカル完結）。
- **入力の占有**: 実行中はミラーリングが最前面を占有し合成クリックを送る。意図しない操作を
  避けるため、実行前に他の重要操作を完了し、キルスイッチ（ウィンドウを閉じる／ホットキー）を把握しておくこと。

### 17.5 実装状況（`tools/autolive.py` / 実機検証で確定）

PoC として、実際に**ライブを自動で繰り返しクリアし続けるスクリプト** `tools/autolive.py` を実装・実機検証した。
仕様書当初の汎用 FSM を、実機調査で判明した以下の事実に基づき簡素化している。

**実機で判明した重要事実**
1. **ライブはノーツを全部見送っても完走し RESULT に到達する**（クリア自体は命中不要）。
   タップ判定円を連打するとスコアが入り、前面維持にも寄与する。
   → 「タイミング検出による打鍵」は必須ではなく、まず**4つのタップ円の連打**で実用化した。
2. **画面取得は `mss`（フレームバッファ直読）必須**。`screencapture -l<windowid>` は
   ウィンドウのフォーカスを奪い**ゲームを PAUSE させる**ため使用不可。mss は約 35fps 取得可・PAUSE 非誘発。
3. **ライブ中にミラーリングのフォーカスが外れると iOS アプリが background 化し PAUSE する**。
   完全防止は困難（高速再アクティブ化でも数秒で PAUSE する）。
   → **「PAUSE を検出したら即・再開」で対処**（ユーザー指示とも一致）。連続タップでも防ぎきれない。
4. **ループは「ライブ ⇄ リザルト」だけで回る**。リザルト系を進めると最後に「もう一度→はい」で
   **同じ曲が再開**するため、毎回ホーム→イベント→楽曲選択…と辿る必要はない。
5. **ウィンドウのタイトルバー有無で内容が上下にズレ・約0.86倍に縮小**する。
   → ゲーム内容矩形（暗い領域）を毎フレーム検出して座標補正＋テンプレはマルチスケール照合。
6. **状態判定は「明るさゲート＋テンプレ照合」が堅牢**。小テンプレのマルチスケール照合のみだと
   誤検出が多発した。確定した判定:
   - 「PAUSE」文字テンプレ一致 → PAUSE（暗背景でも確実、score≈1.0）
   - 画面平均輝度 < 65 → ライブ中（暗い）→ タップ円連打
   - 明るい → メニュー/リザルト。`RANK UP!`/`申請する`/`Result` 等を高閾値で個別判定、
     どれでもなければ**確定ボタン候補位置を巡回タップ**して前進（「はい」「申請する」「もう一度」等）。

#### (E) ゲームプレイ中の自動 PAUSE は intrinsic（最重要・実験で確定）
ライブ中、ゲームが**自分の PAUSE メニューを定期的に表示**する。複数の制御実験で原因を切り分けた:

| 実験 | 操作内容 | 結果（PAUSE までの時間 / 頻度） |
|------|----------|--------------------------------|
| 純粋オブザーバ | grab のみ・クリック/activate/カーソル一切なし | ゲーム開始 **0.7秒**で PAUSE、以後 30秒そのまま |
| カーソルジグル | 実カーソルを 1.2s ごとに移動(warp+moved) | 40秒で **9回**（≈4.7秒周期、baseline と同じ＝無効） |
| 高頻度連打 | 円を 0.03s ごと(≈32回/秒)に連続タップ | 再開後 **約3〜5秒**で PAUSE |
| カーソル同位置クリック | warp+moved+click を各タップ点で実施 | 30秒で **7回**（baseline 同等＝無効） |
| caffeinate | `caffeinate -disu`（アイドル/スリープ/表示抑止+活動宣言） | 効果なし |
| autolive(run3) | 円連打＋0.4s ごと activate_fast | 600秒で **129回**（≈4.7秒周期）、0クリア |

**確定した事実**:
- iPhone ミラーリングは PAUSE 中も**フロントモスト＆アクティブ**（`isActive()==True`）。
  → **フォーカス喪失が原因ではない**。ホスト側コマンド実行（ポーリング）も無関係だった。
- **合成クリック(CGEvent)も実カーソル移動も、PAUSE を完全には防げない**。
  ただし**タップは PAUSE 到来を遅延**させる（無操作 0.7秒 → 連打時 6〜8秒）。
- これは **iPhone ミラーリング経由で iOS アプリが定期的に inactive 化（background 相当）し、
  ゲームが resignActive で PAUSE メニューを出す**挙動と考えられる。genuine な実機タッチが
  ないと iOS 側がアプリをアイドル扱いする、プラットフォーム由来の制約。

**結論（複数実験で確定）**:
- **Mac 側のいかなる合成入力（クリック・カーソル移動・カーソル同位置クリック・caffeinate）でも
  この PAUSE は防げない**。アプリはフロントモスト・アクティブのまま、ゲームが定期的に PAUSE する。
- **mss の画面取得(grab)も無関係**（grab を一切せず18秒タップし続けても PAUSE する＝grab は原因でも
  防止策でもない）。
- PAUSE 周期が短い（≈3〜5秒）場合は再開カウントダウンの巻き戻しで**新規曲がほぼ進まない**。
  **決定的検証: 無人で 42分・691回の PAUSE→再開 を繰り返しても 0 クリア**（1曲も完走せず）。
  691サイクルあれば net 進行が少しでも正なら必ず完走するはずで、完走しない＝
  **mss ミラーリングの app-suspension からの「再開」は曲を巻き戻し、再生分を相殺する**
  （実質「待てば終わる」問題ではない）と確定。
- 過去に観測した完走（Result 到達）は、**PAUSE が起きない連続再生ウィンドウ**（=実機操作・
  在席条件）で得られたものであり、無人の再開サイクル累積では得られない。
- **帰結: 無人・完全自動での連続クリアは、この PAUSE が起きる環境では不可能**。
  正常動作には PAUSE が起きない条件（iPhone 自動ロック無効＋実行中の在席で genuine 入力を
  供給）が必須。これはプラットフォーム制約であり、本ツールのコードでは解決できない。
- **PAUSE があっても曲は net で進行し、累積タップで必ず完走する**（実機で複数回 Result 到達を確認）。
  ただし効率が低く（再開ごとに 3秒カウントダウン＋わずかな巻き戻し）、**PAUSE 多発条件下では
  1ライブの実完走に 8〜10分程度**かかる（300〜480秒では未完のことがある）。

**帰結（実装方針）**:
- PAUSE は不可避と割り切り、**検出したら即・再開**（`P_RESUME=(0.69,0.76)`）。再開直後の
  カウントダウンは暗い＝gameplay 扱いなのでそのままタップ円連打を継続 → 自然に曲が進む。
- **本ツールは「PAUSE を高速に再開し続ける」ことで、低速ながらライブを連続クリアし続ける**。
- 運用上の最善策（ユーザー向け・高速化）: **iPhone の自動ロックを「なし」にし、実行中は
  Mac に物理的に在席して時々トラックパッド等を操作する**。genuine な実機/HID 入力がある条件では
  PAUSE がほぼ起きず 1ライブ≈90秒で回る（§17.5 の初期検証はこの条件下だったと推定）。

> **【重要・後日解決】上記「ソフト側からの根本回避は確認できていない」は §17.6 F で解決した。**
> 通常の合成クリック（`source=None`）が genuine 入力として扱われなかったのが原因で、
> **HIDSystemState のイベントソース**で実カーソルを動かしてクリックすれば PAUSE は起きない。

### (F) ライブ中の自動PAUSEの解決策（2026-06-05 実機で確定・実装済み・最重要）

§17.6 E で「Mac 側の合成入力では PAUSE を防げない」としたが、**原因と解決策を特定した**。

**原因**: iPhone ミラーリングは「**genuine な HID 入力**」が数秒ないと iOS アプリをアイドル化し
PAUSE させる。通常の `CGEventCreateMouseEvent(None, ...)`（イベントソース=None）で送る合成
クリックは、ゲームには届く（タップは効く）が、ミラーリングのアイドル判定をリセットしない。

**解決策（実装済み, `autolive.py` `_click_screen`）**: クリックを以下の形で送る。
1. `CGEventSourceCreate(kCGEventSourceStateHIDSystemState)` で**イベントソースを作成**。
2. 各クリックで **`CGWarpMouseCursorPosition` で実カーソルをクリック点へ移動** →
   `MouseMoved` → `LeftMouseDown` → `LeftMouseUp` を、上記ソース付きで `kCGHIDEventTap` に Post。
3. 補助として `caffeinate -dimsu` を実行中だけ起動（アイドル/スリープ/表示消灯の抑止）。

**検証（実機・切り分け）**:
- 通常合成クリック(None): 30秒で PAUSE 約6回（baseline）。
- caffeinate のみ / 実カーソル移動のみ: 効果なし（各 7〜9回）。
- **HIDSystemState ソース + 実カーソルワープ + caffeinate: 30秒で PAUSE 0回**。
- これを autolive に実装して周回: **PAUSE 0 のまま 1ライブ≈115秒で完走→クリア計上→
  きなこパン自動回復（ステラ不使用）→次ライブ、を無人で確認**（pauses=0, clears 加算, life 加算）。

**副作用と注意**:
- **実マウスカーソルがクリック点へ次々ワープする**（ユーザーのカーソルと競合する）。実行中は
  Mac のマウス操作を控えること。これは genuine 入力として認識させるための必須挙動。
- ゲームが連続再生されるため**タップ円が実際にノーツに当たる**ようになり、GRADE/スコアが
  上がる（全ミスではなくなる＝コンボ・スコア課題にも寄与）。
- メニュー画面でもカーソルがワープするが無害。`--dry-run` 時はクリックしない（ワープも無し）。
