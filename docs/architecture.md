# アーキテクチャ

## 4. システム構成・アーキテクチャ

### 4.1 全体構成（メインループ）
```
        ┌─────────────────────────────────────────────┐
        │                 State Machine                │
        │  (周回 / ポップアップ / スタミナ / 停止条件)  │
        └───────▲──────────────────────────┬──────────┘
                │ 認識結果                  │ 操作指示
        ┌───────┴───────┐          ┌───────▼───────┐
        │  Recognition  │          │   Actuator    │
        │ Template/OCR  │          │ 最前面化+Click │
        └───────▲───────┘          └───────┬───────┘
                │ 画像                      │ CGEvent
        ┌───────┴───────┐          ┌───────▼───────────┐
        │   Capture     │          │ iPhone Mirroring   │
        │ (mss→crop)    │◄─────────┤  Window (前面)     │
        └───────────────┘  screen  └────────────────────┘
```
処理は「**キャプチャ → 認識 → 状態判定 → 操作**」を1サイクルとするループ。

### 4.2 コンポーネント分割
| 層 | 役割 |
|----|------|
| Capture（画面キャプチャ） | ミラーリングウィンドウ領域の画像取得（`mss` で全画面取得→クロップ） |
| Recognition（画像認識） | テンプレートマッチング・OCR で現画面状態と要素位置を特定 |
| State Machine（状態管理） | FSM。現状態の判定・アクション選択・遷移制御 |
| Actuator（操作実行） | ミラーリング最前面化 → CGEvent によるタップ/スワイプ |
| Config / Logger / Safety | 設定読込・ログ出力・キルスイッチ・ウォッチドッグ |

### 4.3 最重要の技術制約（設計を規定）

> **iPhone ミラーリングへの合成クリック（CGEvent）は、macOS が入力を「最前面アプリ」に
> のみルーティングするため、iPhone ミラーリングが最前面かつ同一 Space にある間しか
> 機能しない。** バックグラウンドウィンドウへ直接入力を注入する API は存在しない。

帰結:
- **実行中は iPhone ミラーリングが画面を占有**する（Mac を他作業に使えない）。専用周回前提。
- 各操作の直前にミラーリングを `activate`（最前面化）し、短い settle 待ち（約 200ms）を入れる。
- 制御ターミナルとミラーリングウィンドウは **同一 Space**（同じデスクトップ）に置くこと。
- **ハードキルスイッチ = ミラーリングウィンドウを閉じる**（入力が即座に止まる）。
- `CGWindowListCreateImage` は macOS 15.0 で廃止 → キャプチャは `mss` を採用。
  ウィンドウの **列挙**（`CGWindowListCopyWindowInfo` による bounds 取得）は引き続き利用可。

### 4.4 座標系の扱い
- ミラーリングウィンドウ原点 `O=(Ox, Oy)` は **ポイント**（`kCGWindowBounds` より取得）。
- `mss` のキャプチャ画像は **ピクセル**（Retina では 2x）。
- スケール `s = NSScreen.backingScaleFactor`（**ハードコードせず実行時取得**。外部モニタでは 1.0 もあり得る）。
- 画像内マッチ位置 `(mx, my)`（ピクセル）→ クリック先の画面ポイント:
  `screen_pt = (Ox + mx/s, Oy + my/s)`。クリックはマッチ矩形の中心。
- 逆変換: `(px, py) = ((screen_x - Ox)*s, (screen_y - Oy)*s)`。

## 5. 機能要件

### 5.1 ライブ周回機能
FSM（「6. 状態遷移仕様（FSM）」）に基づき、ホーム → イベントページ → ライブ選択 →（楽曲選択）→ 編成確認 →
スタミナ確認 → ライブ開始（AUTO 有効化）→ AUTO 進行待ち → リザルト → 報酬受け取り
→ ループ判定、を自動で繰り返す。「もう一度」ボタンがあればショートカット利用（設定可）。

### 5.3 ポップアップ処理機能
- 各待機サイクルで、期待テンプレの前に **ポップアップ群を優先走査**。
- 対象: レベルアップ / ログインボーナス / お知らせ・告知 / 通信エラー / 汎用 OK・×・閉じる。
- 種別ごとの後処理（例: 通信エラーは「リトライ」優先）。閉じたら割込み元状態へ復帰。

### 5.4 停止条件機能
以下のいずれかで安全停止（または異常停止）:
1. 周回数 ≥ `target_loop_count`（→ SAFE_STOP）
2. 回復アイテム枯渇 かつ `stop_on_item_depletion=true`（→ SAFE_STOP・理由付き）
3. 累計pt ≥ `target_event_points`（OCR・任意機能、null で無効）（→ SAFE_STOP）
4. キルスイッチ押下（→ SAFE_STOP）
5. 連続エラー回数 ≥ `max_consecutive_errors`（→ ERROR_STOP）

### 5.5 進捗トラッキング
周回数（内部カウンタ）、累計pt・スタミナ残量（OCR・任意）を取得しログに記録。
停止時にサマリ（実行周回数・使用アイテム数・経過時間・停止理由）を出力。

## 7. テンプレート画像の管理

### 7.1 命名規則・ディレクトリ構成
```
assets/templates/
├── live/     # home_marker, event_page_marker, live_select_marker, song_select_marker,
│             # formation_marker, live_start_marker, playing_marker, result_marker,
│             # reward_marker, play_again_marker, auto_button_off, auto_button_on
├── stamina/  # stamina_confirm_marker, stamina_shortage_marker, recover_dialog_marker,
│             # drink_s, drink_m, item_empty_marker
└── popups/   # popup_levelup, popup_login_bonus, popup_notice, popup_network_error,
              # popup_generic_ok, popup_generic_close, back_button, home_button
```
- ファイル形式: PNG（アルファ不要、ロスレス）。
- 命名: スネークケース、状態/役割が分かる名前。設定の `stamina.item` 値はファイル名に対応。

### 7.2 必要テンプレ画像チェックリスト
「17.1 必要テンプレート画像チェックリスト」に集約。実機 UI をキャプチャして用意する。

### 7.3 マッチング方式・閾値
- `cv2.matchTemplate` + `TM_CCOEFF_NORMED`、相関スコア ≥ `match_threshold`（既定 0.85）でヒット。
- テンプレごとに閾値を上書きできる設計が望ましい（小アイコンは高め等）。
- 同一テンプレが複数ヒットする場合は最大スコア位置を採用。

### 7.4 解像度・スケーリング依存
- テンプレ取得時と同一ウィンドウサイズ・スケールでのみ正しく動作（v1）。
- 起動時に `mirroring.expected_resolution` と実ウィンドウサイズを照合し、不一致なら警告。
- ゲーム UI 更新・テーマ変更時は再取得が必要。

### 7.5 ROI（関心領域）
誤検出低減・高速化のため、状態ごとに探索範囲（ROI）を限定可能とする（例: ボタンは画面下部）。
OCR 対象（累計pt・スタミナ・周回数）の ROI 定義は**未実装**。

## 15. テスト方針
- **単体テスト**: 座標変換（`geometry`、純粋関数）、設定バリデーション（`config`）、OCR パーサ。
- **認識回帰テスト**: `tests/fixtures/` に保存したスクショに対しテンプレマッチ結果を検証（実機不要）。
- **結合テスト**: モック画面列で FSM 遷移を検証（actuator はモック）。
- **実機シナリオ**: 数周回の短時間通しで周回成立・停止条件・キルスイッチを確認。
- **dry-run**: `--dry-run` で実クリックなしに遷移ログを確認（テンプレ調整時の安全確認）。

## 17.5 実装状況（`tools/autolive.py` / 実機検証で確定）

PoC として、実際に**ライブを自動で繰り返しクリアし続けるスクリプト** `tools/autolive.py` を実装・実機検証した。
仕様書当初の汎用 FSM を、実機調査で判明した以下の事実に基づき簡素化している。

**実機で判明した重要事実**
1. **ライブはノーツを全部見送っても完走し RESULT に到達する**（クリア自体は命中不要）。
   タップ判定円を連打するとスコアが入り、前面維持にも寄与する。
   → 「タイミング検出による打鍵」は必須ではなく、まず**4つのタップ円の連打**で実用化した。
2. **画面取得は `mss`（フレームバッファ直読）必須**。`screencapture -l<windowid>` は
   ウィンドウのフォーカスを奪い**ゲームを PAUSE させる**ため使用不可。mss は約 35fps 取得可・PAUSE 非誘発。
3. **ライブ中にミラーリングのフォーカスが外れると iOS アプリが background 化し PAUSE する**。
   完全防止は困難（高速再アクティブ化でも数秒で PAUSE する）。
   → **「PAUSE を検出したら即・再開」で対処**（ユーザー指示とも一致）。連続タップでも防ぎきれない。
4. **ループは「ライブ ⇄ リザルト」だけで回る**。リザルト系を進めると最後に「もう一度→はい」で
   **同じ曲が再開**するため、毎回ホーム→イベント→楽曲選択…と辿る必要はない。
5. **ウィンドウのタイトルバー有無で内容が上下にズレ・約0.86倍に縮小**する。
   → ゲーム内容矩形（暗い領域）を毎フレーム検出して座標補正＋テンプレはマルチスケール照合。
6. **状態判定は「明るさゲート＋テンプレ照合」が堅牢**。小テンプレのマルチスケール照合のみだと
   誤検出が多発した。確定した判定:
   - 「PAUSE」文字テンプレ一致 → PAUSE（暗背景でも確実、score≈1.0）
   - 画面平均輝度 < 65 → ライブ中（暗い）→ タップ円連打
   - 明るい → メニュー/リザルト。`RANK UP!`/`申請する`/`Result` 等を高閾値で個別判定、
     どれでもなければ**確定ボタン候補位置を巡回タップ**して前進（「はい」「申請する」「もう一度」等）。

**ユーザー指定の運用ルール（実装済み）**
- ライブブースト **3倍**、難易度 **EASY+**、楽曲は任意（編成は先頭フレンドを選択）。
- 本日の課題／獲得一覧／RANK UP ポップアップ → **右上 × で閉じる**。
- データダウンロード確認 → **必ずダウンロード**。
- EVENT RESULT のフレンド申請 → **申請する**。新エピソード開放・もう一度 → **はい**。
- PAUSE → **再開**。

**検証結果**: 実機で**ライブを自動クリアし、RANK UP・フレンド申請・もう一度→次のライブ**まで
一連を無人で繰り返すことを確認（1ライブ≈90秒）。`mss`＋明るさゲート＋座標補正で安定動作。

**v0.3 で確定・実装した事項（2026-06-04 追補）**
- **PAUSE 再開バグ修正**: 見出しでなく固定の再開ボタン位置 `P_RESUME` をクリック（[navigation.md](navigation.md)「(D) PAUSE メニューの正確な仕様（重大バグ修正済み）」）。
- **ポストライブ・フローをテンプレ駆動に刷新**（盲目巡回 `ADVANCE_POINTS` を廃止）:
  判定順 `lifeshort → friendreq → replay → rankup → closex → download → result → menu`。
  per-song Result / EVENT RESULT は**中央タップ**で送る（下端タップでは進まない）。
- **RANK UP** は固定×位置 `P_RANKUP_X=(0.802,0.251)` で閉じる（プレイヤーランク上昇時に
  **LIFE が MAX 回復＆上限増加**するため、LIFE 供給源にもなっている）。
- **連続ライブ再プレイ「はい」** を `replay_title.png` で検出して押下（ループの要）。
- **LIFE 回復＝きなこパン**（[navigation.md](navigation.md)「(D-LIFE) LIFE 回復ダイアログ＝きなこパンで回復（ステラ厳禁）— 2026-06-04 実測・実装済み」）。**ステラは一切クリックしない**多重安全装置。
- **ステラ安全装置**: 未知の明るいダイアログ／閉じられないポップアップは
  `STUCK_STOP_SEC`(25s) で**停止＋スクショ**。確定ボタンの盲目クリックを完全廃止。
- 座標系を整理: スクショ実測座標は `click_window`（ウィンドウ相対）で扱う。

**残課題 / 今後**

  実カーソルワープでクリックすることで PAUSE 0・無人で連続クリア可能になった。

  `open -b com.apple.ScreenContinuity` 相当の再接続を将来自動化する余地がある。
- ホーム→イベント→楽曲選択 の初期ナビゲーション自動化（現状は手動で楽曲開始まで進めてから起動）。
- ~~ノーツのタイミング検出による打鍵~~ → **実装済み（既定 `--tap-mode timing`）**。
  各タップ円に明るいノーツが到達した瞬間を円ROIの「白っぽい画素割合」が暗いベースラインから
  跳ね上がることで検出してタップする（`_gameplay_timing`/`_note_present`）。
  - 円ごとのEMAベースライン（静穏時のみ更新）で持続的な演出を吸収し、過渡的な到達のみ発火。
    `NOTE_DEBOUNCE_SEC`(0.18s) で1ノーツ=1タップ・タップ波紋の再発火を抑止。

  - **しきい値調整**: `--calibrate` で各円ROIの white割合 統計（min/p50/p95/max）を出力。
    `--note-trigger/--note-lead/--note-roi` で即上書き可能。定数は autolive.py 冒頭 `NOTE_*`。
  - **種別の限界（ベストエフォート）**: タップノーツ最適化。フリック/スライド/ロングは
    **頭だけ取得＝部分点**（スワイプは source=None で PAUSE 防止が効かないため非対応）。
    画面キャプチャ遅延(±60-100ms)で PERFECT 安定は不可・GOOD帯中心。
  - **フォールバック**: `--tap-mode rotate` で従来の5円50Hz巡回連打（実績あり）。誤チューニング時の保険。
