# 運用

## 現在の推奨構成（2026-07-31 実機で確定）

```bash
# 無人周回。楽曲選択画面から実行する（起動手順は README.md「周回開始コマンド」）
# run_until.sh が最上位。切断中は待機し、supervisor は落ちた autolive を8秒後に再起動する
tools/ops/run_until.sh                                       # 対話（推奨）
nohup tools/ops/run_until.sh <target_epoch> > /dev/null 2>&1 &   # 自動化から呼ぶとき

# 成績を並走して蓄積（チューニングの効果判定に使う）
nohup python -u tools/ops/result_log.py 7200 <tag> > /tmp/i7dbg/reslog.log 2>&1 &
python tools/ops/result_log.py montage <tag>
```

supervisor の打鍵オプションは `--flick --auto-circles`（`I7_TAP_OPTS` で**丸ごと差し替え**、
`I7_TAP_EXTRA` で**既定に追記**）。`--note-lead` は指定せず `autolive.py` の既定（0.02）に従う。
対話モードは `I7_TAP_EXTRA` 側を使う（既定値の真実の情報源を supervisor 1箇所に保つため）。

到達している水準（Don't Analyze Me / EASY+ / ブースト3倍）:

| 指標 | 値 |
|---|---|
| SCORE | 33.8万〜34.3万（BEST 545,300） |
| PERFECT / GOOD / BAD / MISS | 17 / 158〜160 / 2〜4 / 5 |
| COMBO | 52〜64 |
| ループ周波数 | 26〜37 FPS（判定3,000〜4,400フレーム/ライブ） |
| 1周あたり | 約83秒 |

**残課題**: GOOD 158 に対し PERFECT 17。判定は当たっているが精度が GOOD に偏っており、
lead をさらに詰める余地がある。効果は1ライブでは誤差（±5%）に埋もれるので、
`result_log.py` で分布を貯めて比較すること。

## 実機を動かす際の確認項目

実機（iPhone ミラーリング）でしか確認できない項目のチェックリスト。**ログ文字列と数値で
判定できる形**にしてある。周回を止めると LIFE を消費するので、上から順に確認して
「異常があれば次に進まない」運用にすること。

判定に使うログは `/tmp/i7_autorun.log`（autolive）、`/tmp/i7_supervisor.log`（supervisor）、
`/tmp/i7_runner.log`（run_until.sh）。

### A. 起動前（周回を始める前に必ず）

ここで異常があれば**ライブに入る前に止める**（LIFE を使わずに済む）。

| # | 指標 | 取り方 | 正常 | 異常の意味 |

### 停止しきい値の早見表

安全停止に至る条件。ログに出たら**何が起きたか**の手掛かりになる。

| 定数 | 値 | 発火条件 | ログ |
|---|---|---|---|
| `STUCK_STOP_SEC` | 25.0秒 | 未知画面／閉じられないポップアップに滞留 | `[warn] 未知画面に Ns 停滞` ほか |
| `RESULT_STUCK_SEC` | 30.0秒 | Result 送りが進まない | `[warn] Result送りが Ns 進まず停滞` |
| `GAMEPLAY_TIMEOUT_SEC` | 240.0秒 | 暗い画面が続く（切断オーバーレイの誤認など） | `[warn] gameplay が Ns 継続` |
| `MAX_LIFE_RECOVERS` | 6 | LIFE 不足が連続（きなこパン枯渇の可能性） | `[warn] LIFE不足が継続` |
| `MIN_LIVE_SEC` | 20.0秒 | これ未満の gameplay はクリアに計上しない | — |

### 打鍵パラメータを変えるときの手順

1. **C-1（ループ周波数）と C-2（打鍵回数）を先に確認する。** 30 FPS を大きく下回るなら
   パラメータではなくそこを直す
2. 変更は**1つずつ**。2つ同時に変えると効果を切り分けられない
3. `tools/ops/result_log.py` で**複数ライブ**回してから比較する（単発は誤差に埋もれる）
4. ライブの途中で止めない。リザルト画面になってから入れ替える
   （`detect()` が `gameplay`/`pause` を返す間は待つ）

## チューニングの進め方（順序を守る）

1. **まず打鍵回数とループ周波数を見る**（ライブ終了時のログ `打鍵N回 / 判定Mフレーム`）。
   30 FPS を大きく下回るなら、パラメータではなくそこを直す
2. 打鍵回数がノーツ数を下回る → 検出の問題（`--auto-circles` の効き、しきい値）
3. 打鍵回数は足りているのに MISS/GOOD が多い → タイミングの問題（`--note-lead`）
4. 変更したら `result_log.py` で**複数ライブの分布**を見て判定する。単発比較は誤差と
   区別できない（実測で同一設定でも ±5% ばらつく）

## 17.7 長時間無人運用の運用知見（2026-06-07 自律周回セッションで確定）

- **検出の前提は「ミラーリングが最前面」。** 合成クリックの前提（§概要・CGEvent ルーティング）と
  同じく、**画面分類も前面化が前提**。`detect()` は明るさゲート（`DARK_THRESH=65`）→テンプレ照合の
  順で、楽曲選択は本来 mean≈76・`songselect`(NEXT) 照合 1.00 で確実に当たる。しかし他ウィンドウが
  ミラーリングを覆うと mean≈60 へ低下＋NEXT が隠れ、`bright<65` の暗パス→救済 songselect も
  閾値(0.85)未達となり **`gameplay` と誤分類**する（イベント装飾「KEEP OUT」テープも mean を下げる
  要因）。`--dry-run` は前面化しないためこの罠に嵌まりやすい。**実運用（前面化あり）では正常**。
  手動で検出を確かめるときは `driver.activate()` してからキャプチャすること。
- **SE サイズ窓（529×334, scale 2.0）の楽曲選択(EASY 選択時)の実測スコア:**
  `songselect` 1.00 / `closex` 0.848(閾値 0.87・**やや近い**ので将来イベント装飾で誤発火しうる) /
  `replay` 0.74 / `formation` 0.70。判定順は `closex`→…→`songselect` のため、`closex` が 0.87 を
  超えると songselect 前に誤って閉じる動作に入る点に注意（現状は安全マージン内）。
- **無人運用の標準手順:** `tools/ops/supervise_autolive.sh <target_epoch>` を `nohup … &` で起動。
  autolive がクラッシュ/終了しても 8 秒後に自動再起動し、target 到達で停止する。ログは
  `/tmp/i7_autorun.log`（autolive・`python -u`）/ `/tmp/i7_supervisor.log`（再起動履歴）。
  起動直後の正常系ログ例: `楽曲選択→EASY→NEXT` → `フレンド選択` → `編成→START` → ライブ突入。
- **打鍵パラメータのチューニングを反映する方法:** supervisor は autolive を `--max-seconds=残り`
  で一発起動するので走行中は再起動しない。`NOTE_*` 既定値を編集 → **autolive の子プロセスだけを
  kill**（supervisor は残す）→ supervisor が更新後コードで自動再起動、で反映できる。

## 17.2 トラブルシューティング
| 症状 | 想定原因 | 対処 |
|------|----------|------|
| 何も操作されない | アクセシビリティ権限不足／ミラーリングが最前面でない | 権限付与＋ホスト再起動、`doctor` 実行 |
| キャプチャが真っ黒 | 画面録画権限不足／iPhone スリープ | 権限付与＋再起動、iPhone を起こす |
| ボタンを押せない/ずれる | ウィンドウサイズ変更・解像度/スケール変化 | サイズを戻す、テンプレ再取得、`expected_resolution` 設定 |
| すぐ ERROR_STOP | テンプレ未整備・閾値過大・UI 更新 | テンプレ確認・`match_threshold` 調整・再取得 |
| 途中で止まる | 未知ポップアップ・通信エラー | ポップアップテンプレ追加、ログのスクショ確認 |
| `--dry-run` だと楽曲選択を `gameplay` と誤検出する | dry-run は**前面化しない**ため他ウィンドウ（VS Code 等）がミラーリングを覆い、画面が暗くなり（mean≈60<65）NEXT も隠れて songselect テンプレが閾値未満になる | これは dry-run 固有の見かけ上の問題。実運用は autolive が `activate()` で前面化するので発生しない。**検出を手動検証するときは先にミラーリングを前面化**してからキャプチャすること（本書「17.7 長時間無人運用の運用知見（2026-06-07 自律周回セッションで確定）」）|

## 16. 既知のリスク・制約
1. **最前面占有**: 実行中は Mac を他用途に使えない（プラットフォーム由来、回避不可）。
2. **テンプレ脆性**: ウィンドウリサイズ・ゲーム UI 更新で破綻 → サイズ固定・閾値調整・再取得運用。
3. **TCC 権限の劣化**: macOS 更新後に無言で失敗 → `doctor` で検知し、再付与＋ホスト再起動を案内。
4. **ミラーリング遅延・フレーム欠落**: 認識失敗時はリトライ／復帰で吸収、黒画面へ連打しない。
5. **OCR 誤読**: 正規表現抽出＋範囲チェックで防御、テンプレを優先。
6. **通信エラー・メンテ時間帯**: ポップアップ処理で吸収、不能時は安全停止。
7. **規約・アカウントリスク**: 第13章のとおり、利用は自己責任。

## 起動方法（PoC）
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install pyobjc-framework-Quartz pyobjc-framework-Cocoa opencv-python mss numpy Pillow
# iPhone ミラーリングでアイドリッシュセブンを起動し、イベントのライブを1回開始しておく
python tools/autolive.py --loops 50 --max-seconds 7200
# 動作確認: python tools/autolive.py --loops 2 --verbose
```
※ 事前に macOS の「画面収録」「アクセシビリティ」権限を実行ホスト（ターミナル等）へ付与すること。
※ **実行中はホスト側で他コマンドを叩かない**（フォーカスを奪い PAUSE を誘発するため。[navigation.md](navigation.md)「(E) ゲームプレイ中の自動 PAUSE は intrinsic（最重要・実験で確定）」）。
