# PAUSE 画面になる原因

ライブ中に PAUSE メニューが出る原因**だけ**をまとめた早見表。復旧手順や周回運用は
[`README.md`](README.md) / [`screen-flow.md`](screen-flow.md) を見ること。
個々の実験ログと検証の生データは [`device-findings.md`](device-findings.md) にある。

PAUSE は症状が全部同じ（**約4.5〜6秒周期で PAUSE ↔ 再開、SCORE は `000000000` のまま**）なのに、
原因が5つあって対処が正反対になる。**症状で判断せず、下の識別表で原因を先に確定すること。**

---

## 0. 大前提: PAUSE は「アイドル判定」で出る

iPhone ミラーリングは **genuine な HID 入力が数秒ないと iOS アプリをアイドル扱いにして
PAUSE させる**。したがって PAUSE の原因は必ず次のどちらかに分類される。

- **(あ) 入力がアイドル判定をリセットできていない** → 原因 A / D / E
- **(い) アプリが resignActive → becomeActive を起こしている** → 原因 B / C

**完全ゼロ入力なら PAUSE しない**わけではない。逆で、**無入力だと約1秒で PAUSE してそのまま
戻らない**（`tools/probes/pure_observe.py`）。検出される `pause` は本物のメニューであって
テンプレ誤検出ではない（pause_score ≈ 1.0・明るさ ≈ 74）。

---

## 1. 原因の識別表

**上から順に潰す。** 判定材料は全部ログか probe で取れる。

| # | 原因 | 決め手（これで確定する） | 状態 |
|---|---|---|---|
| A | 合成クリックのイベントソースが `None` | `_click_screen` が `kCGEventSourceStateHIDSystemState` を使っていない | **解決済み**（2026-06-05） |
| B | `_keep_front` の activate 連打 | `_keep_front` が最前面でも `activate_fast()` を呼んでいる | **解決済み**（2026-06-07） |
| C | 他アプリが最前面を奪う | PAUSE 時の `NSWorkspace.frontmostApplication` が **ミラーリング以外** | 運用で防ぐ |
| D | 再接続後の「病気セッション」 | PAUSE 時の最前面が**毎回ミラーリング**なのに PAUSE する | **ミラーリングを繋ぎ直す** |
| E | 単なる無入力 | そもそも打鍵していない（`--dry-run`・エンジン停止・キャリブ中） | 設定ミス |

**C と D の切り分けが最重要。** 症状が完全に同じで、対処が「Mac 側の運用」と
「iPhone 本体の再起動」に分かれる。判定は最前面アプリのログ1行で決まる。

`autolive.py` は PAUSE のたびに最前面アプリ名をログに出す:

```
PAUSE → 再開 (front=iPhoneミラーリング)                        ← 原因 D の候補
PAUSE → 再開 (front=Ghostty)  <<< 最前面を奪われている（原因C）  ← 原因 C 確定
```

`front=` が**毎回ミラーリング**なら D（**ミラーリングを繋ぎ直す**）、**一度でも他アプリ**なら C（運用）。
ライブを走らせずに観測だけしたい場合は `tools/probes/focus_probe.py`（最前面と pause 状態の
時系列観測）。ただし **`--tap` は `CIRCLES` を叩く**ので、PAUSE 画面で使うと
「諦める」を踏む（3章参照）。PAUSE 中に起動してはいけない。

## 2. 各原因の中身

### A. 合成入力が genuine と数えられない（イベントソース None）

通常の `CGEventCreateMouseEvent(None, ...)` で送るクリックは、**ゲームには届くのに
ミラーリングのアイドル判定をリセットしない**。タップは効いているので「入力は通っている」と
誤認しやすい。

実測（30秒あたりの PAUSE 回数）:

| 送り方 | PAUSE |
|---|---|
| 通常合成クリック（ソース `None`） | 約6回 |
| `caffeinate` のみ | 7〜9回 |
| 実カーソル移動のみ | 7〜9回 |
| **HIDSystemState ソース + 実カーソルワープ + `caffeinate`** | **0回** |

→ CLAUDE.md 絶対規則 7 の根拠。実装は `autolive.py` の `_click_screen`。

### B. `_keep_front` の activate 連打（2026-06-07 の真因）

**すでに最前面のアプリを再アクティブ化すると、その都度ミラー中の iOS アプリが
resignActive → becomeActive 相当になり、ゲームが PAUSE メニューを出す。**
`_keep_front` が 0.4 秒ごとに無条件で `driver.activate_fast()` を呼んでいたのが原因だった。

- 修正前: **約30回 / 120秒・クリア0**
- 修正後（最前面でない時だけ activate）: **1回 / 120秒・クリア成功**
- `driver.activate()` は**単発でも** PAUSE を誘発する。デバッグ中に気軽に呼ばないこと。

再発監視ポイント: `_keep_front` が無条件 activate に戻っていないか。

### C. 他アプリが最前面を奪う

B の裏返し。ミラーリングが最前面を失うと `_keep_front` が正しく activate し、その activate が
PAUSE を呼ぶ。**つまりフォーカスを奪われること自体が PAUSE の原因になる。**

奪う側になりやすいもの: 通知、ブラウザ、エディタ、そして**周回中に人が Mac を触ること**。

> 実測 2026-08-26: BACK ボタンへの合成クリックが1回丸ごと無視された。全画面を撮ると
> 最前面が Ghostty（ターミナル）だった。**周回中に Mac を操作すると、入力が吸われるうえに
> PAUSE の原因にもなる。**

### D. 再接続後の「病気セッション」（2026-06-08 / 2026-07-30 に再現）

ミラーリングが切断→再接続したあと、**あらゆる合成入力がアイドル判定をリセットしなくなる**
状態に落ちることがある。B とは**別物**。

確定している見分け方:

> **2026-08-26 の実測（最も明快な例）**: 129秒で PAUSE 23回、**23回すべて
> `front=iPhoneミラーリング`**。周期は 4.9 / 4.5 / 4.9 / 4.5 / 4.8 … とほぼ一定。
> フォーカス奪取（原因 C）ならこの規則性は出ない。SCORE は `000000000` のまま。

- PAUSE 検出時の最前面が **15回中15回ミラーリング**（= activate は一度も発火していない）
- 人が一切触らない「完全放置」でも **約4.5秒周期で PAUSE（29回 / 150秒）**
- 周期が一定 → ランダムなフォーカス奪取ではなく、アイドル判定側の問題

**Mac 側の打ち手は出尽くしている。** 総当たりで全滅を確認した入力方式:
`tap`（warp + HID move/down/up）・`touchclick`（本物タップ属性の偽装: subtype=3 / src_pid=0）・
`realclick`・`iohid_move`・**`iohid_click`（`IOHIDPostEvent` による実 HID クリック）**。
UI クリック自体は効く（カードを閉じる・START は押せる）のに、gameplay のアイドルだけ
リセットできない。ミラーリングのクリーン再起動も無効。

**復旧手段（2026-08-28 に確立）: iPhone ミラーリングの接続を一度切り、繋ぎ直す。**

ユーザーが発見。**アプリの再起動ではなく「接続を外して再度ミラーリングする」操作**である点が
重要（アプリのクリーン再起動は 4章のとおり無効）。実測:

| 経過 | 出来事 | 結果 |
|---|---|---|
| 0〜83.6s | 接続したまま周回 | PAUSE **13回**・間隔 4.5〜4.9秒・SCORE `000000000` |
| 83.6s | **切断**（窓が 671x348 → 318x701 の縦長ダイアログへ） | — |
| 108.4s | **再接続** | 以降ライブが進行。SCORE 11,509・グッズdrop |
| 再開後 | 同じ設定で周回 | **PAUSE 0回 / 49秒以上**、その後クリア（打鍵171回・約35FPS） |

切断は autolive のログで `ウィンドウ寸法が変化: 671x348 → 318x701` として観測できる。

**同日に潰れた復旧候補（もう試さなくてよい）:**

- **iPhone 本体の再起動 → ×。** 再起動後2回走らせ、いずれも間隔 4.4〜4.9秒（平均 4.67秒）・
  front は全部ミラーリング・**間隔の伸びなし**。2026-08-26 の反証を追試で再現した。
- **Mac の再起動 → ×。** 長らく「唯一の未検証候補」としていたが、再起動直後の実行でも
  PAUSE 28.0 / 32.7 / 37.2 / 42.0 …（間隔 4.7・4.5・4.8）と全く同じ挙動だった。
  **端末の再起動はどちらも効かない。効くのはミラーリングの接続を張り直すこと。**

以下は原因調査で分かっていること。

- **入力が出ていないわけではない。** `KEEPALIVE_GAP_SEC = 0.6` により、ノーツ無検出でも
  0.6秒ごとに入力を出している。0.6秒おきに入力して 4.67秒周期で PAUSE する＝
  **出している入力がアイドル判定に数えられていない**ことの直接証拠。
- **端末の再起動が効かないことの初出は 2026-08-26**（iPhone 再起動後も 187秒で PAUSE 41回・
  間隔 4.3〜4.9秒・伸びなし）。2026-08-28 の追試で iPhone・Mac とも再現し、上表のとおり確定した。
- 内蔵オートライブ + resume 継続なら病気セッションのままでも進行し、PAUSE 間隔が
  6秒 → 12 → 13 → 79秒 と伸びて**自然治癒しうる**（2026-07-31）。ただし
  1ライブにつきブリンドリンク3個を消費するため、CLAUDE.md 絶対規則 5 と衝突する。
  採るならユーザーの明示的な判断が要る。

### E. 単なる無入力

`--dry-run`、ノーツ検出が全く当たっていない、キャリブレーション中など、
**そもそも打鍵していない**だけ。約1秒で PAUSE して戻らない。
原因 A〜D を疑う前に、ログの `打鍵N回` が 0 でないことを見る。

## 3. 二次被害: PAUSE 中の打鍵が「諦める」を踏む（2026-08-26 実測）

**原因そのものではないが、PAUSE を放置すると起きる最悪の結果なのでここに置く。**

PAUSE の照合は毎フレームではなく `DARK_RECHECK_SEC = 0.7` 秒おきに間引かれている。
そのため **PAUSE が出てから最大 0.7 秒間、autolive はまだ `gameplay` だと思って打鍵し続ける。**
その打鍵は PAUSE ダイアログのボタンの上に落ちる。

671×348 窓・`--auto-circles` 補正後の打鍵点と、PAUSE ダイアログのボタンの実測対応:

| 打鍵円 | 着弾（窓px） | 重なるもの |
|---|---|---|
| 0 | (153, 222) | ダイアログ外（無害） |
| **1** | **(224, 279)** | **「諦める」** |
| **2** | **(445, 279)** | **「再開」** |
| 3 | (517, 221) | ダイアログ外（無害） |

- 円2が「再開」を踏むため、**ログ上は `PAUSE → 再開` が成功しているように見える**。
- 円1が「諦める」を踏むと **「途中で諦めますと報酬を受け取る事ができません。よろしいですか？」**
  が出る。autolive はこれを未知画面として**クリックせず安全停止**する（`stop_reason=unknown_screen`）。
  ここで踏みとどまるので**ライブは失われない**が、放置すると LIFE を払ったライブが宙に浮く。
- 復帰は**キャンセル**（窓相対 `(0.387, 0.788)`）。「諦める」は `(0.611, 0.788)` で、押すと報酬を失う。

> PAUSE ダイアログのボタンは **3つ（諦める / やり直す / 再開）** で、**「諦める」が左端**。
> `P_RESUME = (0.69, 0.76)` は「再開」の上に乗るので再開クリック自体は正しい。
> 事故るのは**再開クリックではなく打鍵のほう**。

## 4. 潰した仮説（もう一度調べる必要はない）

原因調査で否定済み。同じ道を再走しないこと。

- HIDIdleTime を要求している / 合成入力を種類でフィルタしている → **×**（真因は activate 連打だった）
- 端末依存・仮想 HID デバイスが必要 → **×**
- 低電力モード → **×**（OFF を確認しても PAUSE）
- Mac の画面収録／アクセシビリティ権限の失効 → **×**（同一 Mac 起動セッション内で成功→失敗が起きた）
- iPhone ミラーリングのクリーン再起動で直る → **×**（再接続しても病気セッションは継続）
- 本物のトラックパッドタップ属性を偽装すれば直る → **×**（subtype/src_pid を寄せても PAUSE）
