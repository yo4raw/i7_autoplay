# 実機知見

> **PAUSE の原因を切り分けたいだけなら [`pause-causes.md`](pause-causes.md) を見ること。**
> 本書は調査の生ログと経緯（なぜそう結論したか）を残す場所で、原因の早見表ではない。

## PAUSE の解決策（2026-06-05）

[navigation.md](navigation.md)「(E) ゲームプレイ中の自動 PAUSE は intrinsic（最重要・実験で確定）」で「Mac 側の合成入力では PAUSE を防げない」としたが、**原因と解決策を特定した**。

**原因**: iPhone ミラーリングは「**genuine な HID 入力**」が数秒ないと iOS アプリをアイドル化し
PAUSE させる。通常の `CGEventCreateMouseEvent(None, ...)`（イベントソース=None）で送る合成
クリックは、ゲームには届く（タップは効く）が、ミラーリングのアイドル判定をリセットしない。

**解決策（実装済み, `autolive.py` `_click_screen`）**: クリックを以下の形で送る。
1. `CGEventSourceCreate(kCGEventSourceStateHIDSystemState)` で**イベントソースを作成**。
2. 各クリックで **`CGWarpMouseCursorPosition` で実カーソルをクリック点へ移動** →
   `MouseMoved` → `LeftMouseDown` → `LeftMouseUp` を、上記ソース付きで `kCGHIDEventTap` に Post。
3. 補助として `caffeinate -dimsu` を実行中だけ起動（アイドル/スリープ/表示消灯の抑止）。

**検証（実機・切り分け）**:
- 通常合成クリック(None): 30秒で PAUSE 約6回（baseline）。
- caffeinate のみ / 実カーソル移動のみ: 効果なし（各 7〜9回）。
- **HIDSystemState ソース + 実カーソルワープ + caffeinate: 30秒で PAUSE 0回**。
- これを autolive に実装して周回: **PAUSE 0 のまま 1ライブ≈115秒で完走→クリア計上→
  きなこパン自動回復（ステラ不使用）→次ライブ、を無人で確認**（pauses=0, clears 加算, life 加算）。

**副作用と注意**:
- **実マウスカーソルがクリック点へ次々ワープする**（ユーザーのカーソルと競合する）。実行中は
  Mac のマウス操作を控えること。これは genuine 入力として認識させるための必須挙動。
- ゲームが連続再生されるため**タップ円が実際にノーツに当たる**ようになり、GRADE/スコアが
  上がる（全ミスではなくなる＝コンボ・スコア課題にも寄与）。
- メニュー画面でもカーソルがワープするが無害。`--dry-run` 時はクリックしない（ワープも無し）。

## PAUSE 多発の真因と修正（2026-06-07）

**症状（修正前）**: ライブ中に約4.5秒ごとに PAUSE↔再開を繰り返し、ノーツが再開カウントダウンで
流れて全 MISS・クリア0 になっていた。

**真因**: autolive の `_keep_front()` が **0.4秒ごとに無条件で `driver.activate_fast()`
（= iPhone ミラーリングアプリの再アクティブ化）を呼んでいた**こと。**既に最前面のアプリを
再アクティブ化すると、その都度ミラー中の iOS アプリが resignActive→becomeActive 相当となり、
ゲームが PAUSE メニューを出す**。`_keep_front` はもともと「ミラーリングを最前面に保ち合成クリックを
届かせる」ための補助だったが、最前面のまま呼び続けたことが裏目に出ていた。

**修正（実装済み）**: `_keep_front` を **「最前面でない時だけ activate する」** に変更
（`_mirror_is_front()` を `NSWorkspace.frontmostApplication` で判定）。ライブ中はミラーリングが
最前面のままなので再アクティブ化が起きず、PAUSE しなくなる。最前面を失った時だけ復帰させる。

**検証**: iPhone SE で **PAUSE 1回 / 120秒・★ライブクリア確認**（修正前は ≈30回/120秒・0クリア）。
合成クリック（HIDソース+ワープ, 本書「PAUSE の解決策（2026-06-05）」の `_click_screen`）はそのままで問題なく打鍵・クリアできる。

**切り分けで確認した事実（再発時の参考）**:
- **完全ゼロ入力なら PAUSE しない**（`tools/probes/pure_observe.py`）。検出する "pause" は本物の PAUSE メニュー
  （誤検出ではない。pause_score≈1.0, 明るさ≈74）。
- `driver.activate()`（ミラーリング再アクティブ化）は単発でも PAUSE を誘発する。
- 本物のトラックパッドタップは PAUSE しない。本物タップは CGEvent 上 `subtype=3`(NX_SUBTYPE_MOUSE_TOUCH)・
  `src_pid=0`(実機由来)、合成は `src_pid` が投稿プロセスPIDになる（偽装不可）が、**これは主因ではなかった**
  （activate を連打しなければ合成クリックでもクリアできる）。
- ※調査途中に立てた「HIDIdleTime 要求／合成入力フィルタ／端末依存／要ハード・仮想HID」などの仮説は
  すべて**誤り**だった（真因は上記 activate 連打）。

**再発時の確認**: ライブ中に再び PAUSE 多発したら、まず `_keep_front` が無条件 activate に戻っていないか、
他アプリが頻繁に最前面を奪っていないかを確認する。

**検証/調査用ツール（任意）**: `tools/probes/pure_observe.py`(ゼロ入力観測), `tools/probes/trigger_test.py`(操作種別の
切り分け), `tools/probes/capture_click.py`(本物/合成のイベント属性比較), `tools/probes/idlekeeper.py`(IOHIDPostEvent),
`tools/probes/pause_ab.sh`。`autolive.py` の `_click_screen` 冒頭に実験用 `I7_CLICK_MODE` 環境変数ディスパッチが
あるが、**未設定なら通常動作**（本番運用では設定しない）。

## 画面構造・ノーツ仕様・画面遷移（2026-06-07）

**ライブのノーツ機構（放射型）**: ノーツは**画面中央でスポーンし、4つの判定円（左上/左下/右上/右下）へ
放射状に飛ぶ**。中央=白い球で出現→飛行→判定円で命中。
- **色は飛行中なら判別可能**（拡大で赤ノーツは明確に赤く光る）。**判定円（到達点）では白飛びして色判別不可**。
  → 種別/色の判定は「飛行中に色検出＋追跡」（= `note_engine.py` の track エンジン方式）が必要で、
  現行 timing エンジンの到達点ROIだけでは色を取れない（だから現行は全部タップ＝部分点）。
- 現行 timing エンジンは各円ROIの白割合スパイクでタップ。`--holds` で明るさ持続=長押しを近似可能
  （色非依存）。

**ノーツ種別と必要操作（ユーザー仕様。チェーン構造）**:
- 🔴 **赤**: タップ→フリック（方向不問）。
- 🟢 **緑**: 長押し開始。**次のノーツまで保持**し、その終端ノーツの種別で離し方が決まる
  （次が緑→そのまま/次が赤→フリックで離す 等）。
- 🔵 **青**: スライドしながら長押し。**次の青ノーツまで**保持して離す。
- ＝緑/青は単発でなく「次のノーツへ繋がるチェーン」。終端ノーツ種別でジェスチャが変わる。
- 未対応だと フリック/スライド/ロングは頭だけ＝部分点 or MISS になる（精度が頭打ち）。

**リザルト画面（精度の読取り）**: per-song Result に `PERFECT / GOOD / BAD / MISS`・`COMBO`・`SCORE`・
グレード(S/SS等) が出る。**ベースライン実測（SE・PAUSE修正後）: PERFECT 59 / GOOD 15 / BAD 3 /
MISS 45 / SCORE 124,172 / SS**。MISS が多く、種別対応（特に hold/flick/slide）と timing 調整が削減課題。

**画面遷移（無人周回で観測した実機フロー）**: ライブ→（per-song）Result→（カード型ポップアップを
背景タップで閉じる）→ EVENT RESULT「申請する」（フレンド申請）→ 連続ライブ再プレイ確認「はい」→
（DLダイアログ/ストーリー遷移ダイアログがあれば処理）→ 次ライブ。LIFE不足時はきなこパンで回復
（ステラ厳禁）。再開/開始時は「3・2・1」カウントダウン（暗い=gameplay 扱い）。

**ミラーリングウィンドウ実測サイズ**: iPhone SE ≈ 529×334(スケール2.0, ≈16:9・レターボックス有)、
iPhone 16 ≈ 671×348(≈19.5:9・全画面)。座標は内容矩形相対＋テンプレ機種別variantで吸収。

## 再接続後の PAUSE 再燃（2026-06-08）

**症状**: 夜間に iPhone ミラーリングが切断（「iPhoneが使用されました」等）→朝に再接続した後、
本書「PAUSE 多発の真因と修正（2026-06-07）」の修正（`_keep_front` 条件付き activate）が入っているにもかかわらず、ライブ中に
**約5秒ごとに PAUSE↔再開**が再燃。全 MISS・実質クリア進まず。

**重要: 本書「PAUSE 多発の真因と修正（2026-06-07）」の真因（activate 連打）とは別物**。今回は activate していない（`_mirror_is_front()`=True を確認、
`_keep_front` は発火していない）のに PAUSE する。**この再接続セッションでは、あらゆる合成入力が
ミラーリングの「genuine 入力」アイドル判定をリセットしない**のが原因。

**切り分けで潰した仮説（すべて×＝原因でない）**:
- 低電力モード（ユーザーが OFF を確認後も PAUSE）。
- Mac 側権限/再起動: **同一 Mac 起動セッション**（昨夜の成功〜今朝の失敗で再起動なし、uptime で確認）。
  画面収録/アクセシビリティは不変。ホストは VS Code。
- **入力方式を総当たりしても全滅**（`tools/probes/trigger_test.py` で gap0.4〜0.5s・--resume、各〜5秒ごとに PAUSE）:
  `tap`(autolive実体=warp+HID move/down/up)・`touchclick`(本物タップ属性 subtype=3/src_pid=0/pressure/eventNumber 偽装)・
  `realclick`(押下時間あり)・`iohid_move`(IOHIDPostEvent=HID層注入)。UI クリックは効く（カード閉じ/START 等は反応）
  のに、gameplay の PAUSE アイドルだけはどれもリセットできない。
- **iPhone ミラーリングのクリーン再起動でも×**（`osascript -e 'quit app "iPhone Mirroring"'`→
  `open -b com.apple.ScreenContinuity`。認証不要で再接続したが PAUSE 継続）。
- **activate/フォーカス喪失でもない（本書「PAUSE 多発の真因と修正（2026-06-07）」とは別物だと計測で確定）**: PAUSE 検出時に最前面アプリを
  ログしたところ **15回中15回 front=iPhoneミラーリング**。つまりミラーリングは最前面のままで
  `_keep_front` の activate は一度も発火していない。私(assistant)が監視 Bash を一切打たない
  「完全放置」でも約4.5秒周期で PAUSE（29回/150秒）。周期が iOS アイドルタイムアウト一定値で
  揃う＝ランダムなフォーカス奪取ではなく**アイドル判定が合成入力を genuine と数えていない**こと。
  （切り分けツール: `tools/probes/focus_probe.py` = 最前面とpause状態の時系列観測）。

**結論**: 残る変数は **iPhone 本体側の状態**のみ。再接続でミラーリングの HID/Continuity 入力チャネルが
「合成入力を genuine と見なさない」状態に落ちたと考えられる。**復旧には iPhone 本体の電源再投入
（リスタート）が最有力**。Mac 側ソフトの打ち手は出尽くした。

**昨夜なぜ動いていたか**は未解明（同一コード・同一 Mac 起動で、切断前は本書「PAUSE の解決策（2026-06-05）」の合成入力で PAUSE 0、
切断後は全滅）。再接続セッションの個体差/iPhone 状態依存の可能性。**再発時はまず iPhone を再起動**し、
ダメなら本セクションの総当たり結果を踏まえ Mac 側ではなく iPhone/ミラーリング側を疑うこと。

### 2026-07-30 の再現記録（イベント周回セッション）

同じ症状が再現した。以下は今回の切り分けで新たに確定したこと。

- **症状**: ライブ中に約5秒周期で PAUSE →（自動再開）→ カウントダウン → 再び PAUSE。
  1ノーツも処理できず SCORE は `000000000` のまま。`autolive.py` のログは
  `PAUSE → 再開` だけが 5 秒間隔で並ぶ。
- **`_keep_front` は無関係**（activate 連打の件とは別物）。
  `NSWorkspace.frontmostApplication` は一貫して `iPhone Mirroring` を返し、
  再アクティブ化は発生していない。
- **カーソルのワープは機能している**。`CGEventGetLocation` を 0.4 秒間隔でサンプルすると
  タップ円の座標間を移動しており、`CGWarpMouseCursorPosition` は効いている。
- **`iohid_click`（`IOHIDPostEvent` による実 HID クリック）でも防げない**（新規確定）。

  ```
  $ .venv/bin/python -u tools/probes/trigger_test.py iohid_click 40 0.4 --resume
  DONE mode=iohid_click pauses=8 first_pause=0.389
       ptimes=[0.4, 6.0, 11.5, 17.1, 22.6, 28.1, 33.7, 39.2]
  ```

  40 秒間に PAUSE 8 回。既に無効と分かっていた tap / touchclick / realclick / iohid_move に加え、
  **iohid_click も無効**であることが確定した。Mac 側で試せる入力方式は出尽くした。
- **完全無入力では約1秒で PAUSE し、そのまま復帰しない**。idle 起因であることの裏付け。
- **結論は変わらず: 復旧手段は iPhone 本体の電源再投入。**

## 円の自動キャリブレーションが3つの理由で不発だった（2026-07-31）

`--auto-circles` は実装済みだったが実機で一度も成功しておらず、機種差 47px のズレを
抱えたまま打鍵していた（**MISS 51・グレード B・SCORE 52,779**）。

実測（iPhone16系 671×348）:

| 円 | 打っていた位置 | 実際のリング | ズレ |
|---|---|---|---|
| 0 | (107, 228) | (153, 235) | **x +46** |
| 1 | (221, 294) | (224, 286) | y −8 |
| 2 | (456, 294) | (445, 286) | x −11, y −8 |
| 3 | (564, 228) | (517, 235) | **x −47** |

不発の理由は3つ重なっていた。

1. **許容誤差不足**: `CIRCLE_MATCH_TOL` 0.06 に対し実測ズレは 0.072〜0.074。わずかに超えて
   `match_circles` が None を返し、安全側に倒れて補正を諦めていた → **0.10** へ
   （prior 同士の間隔は最小 0.16 なので隣接円への誤マッチは起きない）
2. **1フレームで断念**: ライブ突入時の1回だけ試すため、リングが未描画の暗転フレームを
   掴んで「検出0円」で諦め、そのライブ全体を未補正で打鍵していた
   → 成功するまで `AUTOCAL_RETRY_SEC` 間隔で再試行
3. **ライブ中は1フレームで4円そろわない**: ノーツ・タップ波紋・演出で検出が 1〜4円に
   ばらつく → `consensus_circles()` で検出を貯めて**中央値で多数決**確定

補正結果は `.autocal_circles.json` へ永続化し、起動時に復元する（supervisor の再起動の
たびに未補正で打鍵する区間が生まれるのを防ぐ。ウィンドウ寸法をキーにするので機種を
変えても混ざらない）。

修正後: **MISS 51 → 4、グレード B → S**（この時点ではまだループが 3.3 FPS だった）。

## 打鍵ループが 3.3 FPS しか出ていなかった（2026-07-31・最重要）

**精度が出ないときに最初に疑うべき問題。** 長期間これに気づかず、パラメータ調整で
埋め合わせようとしていた。

### 症状

- ユーザーから「反応が全体的に遅い」「全然だめ」との指摘
- Don't Analyze Me（184ノーツ）で **MISS 118〜129・COMBO 3〜4・SCORE 6万台**
- 一方 Ache（103ノーツ）では MISS 4 で済んでいたため、密度の高い曲でだけ破綻していた

### 切り分け

**打鍵回数を計測したのが決め手。** ライブ終了時に `打鍵N回 / 判定Mフレーム` を出すよう
instrumentation を追加したところ:

```
★ライブ クリア（通算 1） 打鍵229回 / 判定376フレーム
```

- 打鍵 229回 > ノーツ 184 → **検出不足ではない**（円座標やしきい値の問題ではない）
- 判定 376フレーム / 115秒 = **3.3 FPS** → サンプリング周期 300ms が原因と確定

この計測が無ければ、円座標やトリガしきい値を延々といじる誤った方向へ進んでいた。

### 原因

ライブ中（暗い画面）も `DARK_RECHECK_SEC` おきに PAUSE/楽曲選択をテンプレ照合していたが、
**全画面マルチスケール照合が 1回 147〜246ms** かかる。0.25 秒間隔だとループ時間のほぼ
全部を消費し、打鍵判定は残りかすでしか回らない。

| 処理 | コスト |
|---|---|
| `mss` フレーム取得 | 17〜27 ms |
| ROI 判定 ×4 | 0.2 ms |
| 到達直前の赤検色 ×4 | 0.3 ms |
| **PAUSE/楽曲選択のテンプレ照合** | **147〜246 ms** |

### 対策

- **PAUSE 見出しの探索範囲を限定**。コーパス37枚すべてで x≈0.50・y=0.27〜0.36 と位置が
  安定していたため、`PAUSE_SEARCH_BOX = (0.25, 0.10, 0.75, 0.55)` に絞った。
  照合コスト 147ms → 28ms（5.2倍）。**37枚すべて検出維持・gameplay 誤検出0** を確認。
  PAUSE を見逃すとライブが止まったまま復帰できず周回が死ぬため、速度より
  取りこぼしゼロを優先して検証した（`tests/test_dark_detect_perf.py` で固定）
- `DARK_RECHECK_SEC` 0.25 → 0.7

### 結果

| 指標 | 修正前 | 修正後 |
|---|---|---|
| 判定フレーム/ライブ | 376 | **3,009〜4,433** |
| ループ周波数 | 3.3 FPS | **26〜37 FPS** |
| MISS | 118〜129 | **5** |
| SCORE | 6万台 | **33.8万〜34.3万** |
| COMBO | 3〜4 | **52〜64** |
| 1周あたり | 128秒 | **83秒** |

### 派生する教訓: lead は遅延の代償だった

`NOTE_ROI_LEAD` を 0.025→0.04→0.055 と「最適化」していたが、これは 3.3 FPS の
検出遅れ（最大300ms）を早撃ちで埋めていただけだった。ループを直して遅延が ~27ms に
減った結果、**正しい lead は 0.02**。

**lead が大きい値でしか合わないときはループが遅い可能性を疑うこと。**

## 打鍵ループは速ければ良いわけではない（2026-08-01・要注意）

3.3 FPS → 38 FPS の修正が劇的に効いたため「速いほど良い」と考え、さらに
`_gameplay_timing` 末尾の `time.sleep(0.005)`（毎フレーム5ms）を外して 48 FPS にした。
**結果は有意な悪化だった。**

| 条件 | PERFECT | SCORE | n |
|---|---|---|---|
| 38 FPS / lead 0.02（元） | 54.5 ± 12.3 | 379,675 ± 16,404 | 10 |
| **48 FPS / lead 0.02** | **37.5 ± 9.4** | **361,604 ± 9,469** | 11 |
| 48 FPS / lead 0.012 | 37.3 | 360,101 | 12 |
| 38 FPS / lead 0.02（撤回後） | 49.5 ± 5.8 | 371,210 ± 8,000 | 11 |

- 48 FPS 化で PERFECT −17.0（**3.5σ**）・SCORE −18,071（3.1σ）。GOOD がそのぶん増えた
- 「サンプリングが速くなり早撃ちに寄った」と考えて lead を 0.02→0.012 に下げたが
  **PERFECT 37.3 で変わらず**。タイミングのオフセットが原因ではないと確認できた
- sleep を戻すと PERFECT +12.0（3.6σ）・SCORE +9,606（2.6σ）回復し、
  元の設定との差は 1.2σ / 1.5σ で**統計的に区別できない**＝完全に復帰した

**機序は未解明。** 合成タップを詰めて出すと取りこぼしが増える（ミラーリング側の
入力処理の問題）と推測しているが確証はない。分かっているのは実測の事実だけである。

**教訓**: 3.3 FPS は明らかに遅すぎただけで、38 FPS 以上は逆効果。「速いほど良い」は
検証すべき仮説であって前提ではない。`time.sleep(0.005)` を無駄と判断して外さないこと
（コードにも同じ注意を書いてある）。

### 効果測定は分布で行うこと

同一設定でも PERFECT は ±12 ばらつく。**平均差10を検出するには各条件25ライブ必要**
という計算になり、単発比較では改善と誤差を区別できない。実際、単発で測っていた
「PERFECT 17」は後の分布測定（平均54.5）と大きく食い違っていた。

`tools/ops/result_log.py` で各条件10件以上を貯め、σ で判断すること。
**計測ツール自体も検証してから使うこと**（2026-08-01 に2度、誤ったものを撮っていた:
固定待ちで EXP 画面／白背景のアイテムポップアップをスコア画面と誤選択）。

## 実機A/B: ジッター採用・緑ホールド却下・predict 却下（2026-08-06・数値決着）

### 計測方法（ここが要点）

`tools/ops/result_log.py` は成績欄を切り出してモンタージュにするだけで数値集計をしない、と

実際に全ライブぶんを転記して平均・標準偏差・Welch の t を出し、以下すべてを数値で判定した。

ただし result_log の取得方式には実害があった。`state=="result"` を見てから 0.35s×8 の
バースト撮影をする作りなので、**LIFE不足ダイアログが絡む周回では 12ライブ中8件を取り逃がす**。
きなこパンが希少な状況では取りこぼし＝資源の浪費に直結する。

方式に変えたら取りこぼしはゼロになった（同一条件で 11/11 取得）。

  実装時の実測 0.25〜0.42 秒の**約2倍**であり、保持中に他レーンを落とす危険もその分大きい。

### きなこパンの経済（無人運用の実質的な上限）

LIFE不足ダイアログを実際に捕まえて読んだ値。

- **きなこパン: LIFE 20 回復 / 1個**。EASY 1ライブ = LIFE 15 なので、**実質 1ライブ = 1個**
  （自然回復が追いつかず、回復直後の LIFE 27 → 1ライブで 12 になり次がまた足りない）
- 周回ペース約 135 秒/ライブ ＝ **1時間あたり約 26 個**消費する
- ダイアログの行順は **きなこパン → ステラストーン → 別のきなこパン系（3行目）**
- **ステラ所持数は周回前後で 1013 のまま変化なし**。commit 2ee6495 の「きなこパン行を照合
  してから押す」対策が実機で機能していることを確認した（ログにも毎回 `行確認 score=1.00`）

つまり**無人周回の実質的な上限はパンの残数**であり、時間ではない。開始前に残数を見れば
「何ライブ回せるか」がそのまま分かる（残数 ≒ ライブ数 ≒ 分×2.25）。

### 成績の劣化はログに出ない（2026-08-06・監視設計上の注意）

最良設定でも 26ライブ中1回、MISS が 5 → **11**（SCORE 262k）に落ちたライブがあった。
このとき `i7_autorun.log` には**警告が一切出ていない**（PAUSE・ウィンドウ寸法変化・通信エラー
いずれも無し）。`--predict` が MISS 約10倍でも周回が止まらなかったのと同じ構造で、

> **supervisor は「クリアしたか」しか見ておらず、成績そのものは見ていない。**

ただし **「成績はログから分からない」は言い過ぎだった**。クリア行の **`打鍵N回`** が実用的な
品質指標になる（2026-08-06 追記）。通常は 184ノーツに対し約370打鍵で、**打鍵不足 ÷ 2 が
MISS の超過とほぼ一致する**:

| 打鍵 | 実測 MISS | 目安 `4 + (370−打鍵)/2` |
|---|---|---|
| 236 | 69 | 71 |
| 212 | 76 | 83 |
| 約370（正常） | 4〜8 | 4 |

厳密な予測式ではないが、**スクリーニングには十分**:

- **打鍵 < 330** → 打鍵していない区間があったライブ（大量 MISS）
- **打鍵 > 600** → リザルト見逃しによる2ライブ連結
- **判定フレーム < 4100 / > 5500** も同じ2種類を捉える

つまりログだけの無人監視でも品質低下は検知できる。**リザルト画像を読む経路（PERFECT ラベル
追跡型）は、数値そのものが要るとき（A/B のチューニング）に使う**という切り分けになる。

#### 計測の教訓（今回いちばん価値があるのはここ）

1. **取りこぼしは欠測ではなくバイアスになる。** 旧 result_log は `state=="result"` を見てから
   0.35s×8 のバースト撮影をする作りで、リザルト遷移がもたつくライブほど外す。そういうライブは
   成績も悪い。結果、計測系が勝手に「良いライブだけ」を選び、**実力より綺麗な分布**を出す。
   実際 arms A/B は 25クリア中7件が未取得で、取りこぼしゼロで測り直すと 25件中7件が MISS>5 だった。
   **分散が不自然に小さいとき（sd 0.24 で 17/18 が同値）は、実力ではなく計測を疑う。**
2. **異常ライブは「打鍵していない区間があった」ライブである（打鍵回数で判別できる）。**
   通常は 184ノーツに対し **約370打鍵（ノーツあたり約2打鍵）・判定フレーム約4550・約33FPS**。
   異常ライブでは打鍵が落ち、**打鍵不足 ÷ 2 が MISS の超過とほぼ一致する**:

   | 間隔 | 打鍵 | 判定frames | 打鍵不足 | 実測 MISS |
   |---|---|---|---|---|
   | 135s | 236 | 3,225 | −134（≒67ノーツ） | 69 |
   | 150s | 212 | 3,153 | −158（≒79ノーツ） | 76 |

   ライブ間隔は正常（135〜150s）なので、**曲の一部の時間帯だけループが打鍵していなかった**
   ということ。タイミングや精度の劣化ではない。頻度は約2〜3%（実測 2/85）。**原因は未特定。**

   当初これを「取得プロセスの並走が打鍵ループを飢餓させた」と結論したが、**それは誤り**だった
   （取得1本に統制した後も同頻度で発生し、該当ライブのホールドも 0.92s・正常解除で異常なし。
   緑ホールドの有無とも紐づかない: 緑ON 2/56 / 緑OFF 0/37 は有意差なし）。

3. **リザルト画面を見逃して「2ライブ連結」になることがある。**
   打鍵 884・判定フレーム 9783・間隔 266s と、**すべてが綺麗に2倍**のクリアが観測された。
   リザルトを `detect()` が捉え損ね、ゲームプレイ中の打鍵がリザルトの「TAP SCREEN」等を
   盲目的に送って次のライブへ入ってしまったと考えられる。2ライブ目の成績は記録されない。
   同じ現象が 240s の `gameplay_timeout` 安全網に掛かって周回が停止した例もある（実測2回）。
   **安全網は正しく機能している**が、復旧には人手（または監視側の再起動）が要る。
3. **A/B は必ず同一の取得方式・同一の並走本数で比べる。** さらに時間帯の交絡を消すため、
   検証したい設定を**基準ブロックで挟む**（best → green → best）。前後の基準が一致すれば、
   間の差はその設定によるものと言える。

## Mac のロックは切断と区別できず、待っても復帰しない（2026-08-06）

無人周回が「ミラーリング切断中」と表示したまま復帰しない状態を調べたところ、
**実際には Mac 側がロックされていた**（`CGSessionCopyCurrentDictionary()` の
`CGSSessionScreenIsLocked` が `True`）。ロック中は iPhone ミラーリングが再接続できないので、
iPhone をロックしても周回は再開しない。

`run_until.sh` の `connected()` は**ウィンドウが縦長かどうか**でしか判定していないため、

- iPhone が使われて切断された（→ iPhone をロックすれば自動復帰する）
- **Mac がロックされている（→ 人がロック解除するまで絶対に復帰しない）**

の2つを区別できない。前者は待てば直るが、後者は待つだけ無駄で、しかもログには
「ミラーリング切断中（iPhone をロックすると自動再接続）」と**誤った復帰方法**が出る。

切り分けは1行でできる:

```python
import Quartz
locked = bool(Quartz.CGSessionCopyCurrentDictionary().get("CGSSessionScreenIsLocked"))
```

**ロック中の画面キャプチャは壁紙しか写らない**（アプリのウィンドウは合成されない）。
`CGWindowListCopyWindowInfo` にはウィンドウが `alpha=1.0 / layer=0 / on-screen` として
残り続けるので、ウィンドウ情報だけを見ていると「ウィンドウはあるのに中身が壁紙」という
不可解な状態に見える。**ディスプレイのスリープ中は同じ領域が真っ黒**になる（`caffeinate -u`
で一時的に起こせるが、ロック自体は解除されない）。

改善案（未実装）: `connected()` にロック判定を足し、ロック中は
「Mac がロックされています。ロック解除が必要です」とログ・通知に出す。
